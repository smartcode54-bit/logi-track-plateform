## 🎨 UI/UX Guidelines

### Design System
- Use **shadcn/ui** components from `@/components/ui/`
- Follow dark mode support patterns already in the codebase
- Use **Tailwind CSS** for styling
- Icons from **Lucide React**

### Form Patterns
- Multi-step wizard forms should have:
  - Sticky header with step indicator
  - Sidebar navigation for steps (desktop)
  - Sticky footer with Back/Next buttons
  - Progress indicator showing current step

### Color Conventions
- Primary actions: `bg-blue-600 hover:bg-blue-700`
- Success states: Green tones (`bg-green-*`)
- Warning states: Orange/Yellow tones
- Error states: Red tones (`bg-destructive`)

### 🌐 Translation (MANDATORY)

> **⚠️ ALL UI text MUST be translated. No hardcoded strings allowed.**

### 🆕 New Page Policy (Web & Mobile)
> **If you create a new page, you MUST translate it immediately.**
- **Web (Next.js):** Use `useLanguage()` hook and `t("key")`.
- **Mobile (Flutter):** Use `AppLocalizations.of(context)` (or current project standard).
- **Rule:** No PR shall be approved if a new page contains hardcoded strings.

**When creating or updating any UI component:**

1. **Import the language hook:**
   ```tsx
   import { useLanguage } from "@/context/language";
   const { t } = useLanguage();
   ```

2. **Use translation keys instead of hardcoded text:**
   ```tsx
   // ❌ WRONG
   <Button>Save Changes</Button>
   
   // ✅ CORRECT  
   <Button>{t("saveChanges")}</Button>
   ```

3. **Add translations to `context/language.tsx`:**
   ```tsx
   saveChanges: {
     en: "Save Changes",
     th: "บันทึกการเปลี่ยนแปลง",
   },
   ```

4. **Checklist before commit:**
   - [ ] All visible text uses `t("key")` pattern
   - [ ] All new keys added to `context/language.tsx`
   - [ ] Both `en` and `th` translations provided

### 🗄️ Database Collections (MANDATORY)

> **⚠️ ALL collection names MUST use const variables. No string literals allowed.**

**Define collection names in a constants file:**
```typescript
// lib/collections.ts
export const COLLECTIONS = {
  USERS: "users",
  TRUCKS: "trucks",
  DRIVERS: "drivers",
  SUBCONTRACTORS: "subcontractors",
  ASSIGNMENTS: "assignments",
} as const;
```

**Usage:**
```typescript
// ❌ WRONG - hardcoded string
const docRef = doc(db, "users", id);
const collRef = collection(db, "subcontractors");

// ✅ CORRECT - use const variable
import { COLLECTIONS } from "@/lib/collections";
const docRef = doc(db, COLLECTIONS.USERS, id);
const collRef = collection(db, COLLECTIONS.SUBCONTRACTORS);
```

**Benefits:**
- Typo prevention with TypeScript autocomplete
- Easy refactoring if collection names change
- Single source of truth for all collection names

## 🚦 Compliance & Thresholds (MANDATORY)

> **⚠️ All compliance logic MUST follow these standard thresholds.**

### Warning Levels
1. **Overdue (Red)**
   - Date: Past due (< 0 days)
   - Mileage: Over limit (< 0 km remaining)
   
2. **Due Soon / Expiring (Orange)**
   - Date: 0 - 30 days remaining
   - Mileage: 0 - 2,000 km remaining (User specified)

3. **Incoming (Blue)**
   - Date: 31 - 60 days remaining
   - Mileage: 2,001 - 5,000 km remaining

### Implementation Rule
- Use these constants in both **filtering logic** (List Pages) and **status calculation** (Cards/Widgets).
- Do not hardcode numbers like `1000` or `30` in multiple places; define them once or follow this standard strictly.

## 🚀 Deployment & Routing Standards (MANDATORY)

### Static Export vs Dynamic Routes
> **⚠️ CRITICAL: Firebase Hosting + Next.js Static Export Issue**

- **Problem**: Accessing dynamic routes (e.g., `/admin/trucks/[id]`) directly on Firebase Hosting often triggers a 404/redirect loop because the specific HTML file doesn't exist at the root level.
- **Solution**: Use **Query Parameters** for detail views that fetch data client-side.
  - ❌ **Avoid**: `router.push('/admin/trucks/' + id)`
  - ✅ **Use**: `router.push('/admin/trucks/view?id=' + id)`

### File Hygiene & Duplication
> **⚠️ NEVER leave duplicate or dead files in the codebase.**

- **Refactoring Rule**: If you move logic from `[id]/page.tsx` to `view/page.tsx`, you **MUST DELETE** the old `[id]` files immediately.
- **Why**: Having same-named components (`TruckPreviewClient`) in multiple locations causes:
  1. Build errors (Module resolution conflicts)
  2. Developer confusion (Editing the wrong file)
  3. "Ghost" bugs (Changes not reflecting)

## 🔒 High Security

### Authentication & Authorization
- **Never trust client-side** - Always validate permissions server-side
- **Use Firebase Security Rules** - Restrict database access by role
- **Token validation** - Verify auth tokens on all API routes

### Input Validation
```typescript
// ✅ ALWAYS validate with Zod before saving to database
const result = schema.safeParse(data);
if (!result.success) {
  throw new Error("Validation failed");
}
```

### Sensitive Data
- **Never expose credentials** - Use environment variables
- **Never log sensitive data** - No passwords, tokens, or PII in console.log
- **Sanitize user input** - Prevent XSS, SQL injection, NoSQL injection

### Firebase Security Rules (Example)
```javascript
// firestore.rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // Users can only read/write their own data
    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    
    // Admin-only collections
    match /trucks/{truckId} {
      allow read: if request.auth != null;
      allow write: if request.auth.token.role == 'admin';
    }
  }
}
```

### Checklist Before Deploy
- [ ] No hardcoded API keys or secrets
- [ ] Firebase Security Rules reviewed
- [ ] All user inputs validated with Zod
- [ ] Error messages don't expose internal details
- [ ] Authentication required for protected routes

### Required Fields
```typescript
interface TenantAwareEntity {
  // Ownership identification
  ownerType: "own" | "subcontractor";  // Who owns this record
```

### Usage Example
```typescript

  ownerType: "own",
  subcontractorId: undefined,  // Not needed for company-owned
  licensePlate: "ABC-1234",
  // ...
};

// Creating a truck for a subcontractor

  subcontractorId: "sub_abc123",  // REQUIRED

  // ...
};
```

### Query Patterns
```typescript
// ✅ Fetch only company-owned trucks
const q = query(
  collection(db, COLLECTIONS.TRUCKS),
  where("ownerType", "==", "own")
);

// ✅ Fetch trucks for specific subcontractor
const q = query(
  collection(db, COLLECTIONS.TRUCKS),
  where("ownerType", "==", "subcontractor"),
  where("subcontractorId", "==", subId)
);
```

### Entities Requiring Multi-Tenancy
- ✅ Trucks (`ownerType`, `subcontractorId`)
- ✅ Drivers (if assigned to subcontractor)
- ✅ Assignments (inherit from truck/driver)
- ⚠️ New entities should follow this pattern

## 📜 Immutable Logs Pattern (statusHistory)

> **⚠️ Status changes MUST be logged immutably for audit trail.**

### Implementation
```typescript
interface StatusHistoryEntry {
  status: string;           // The new status
  changedAt: Timestamp;     // When the change occurred
  changedBy: string;        // User ID who made the change
  changedByName?: string;   // Display name for convenience
  reason?: string;          // Optional reason for change
  previousStatus?: string;  // What it was before
}

interface EntityWithHistory {
  status: string;                    // Current status
  statusHistory: StatusHistoryEntry[]; // Immutable log (append-only)
}
```

### Usage Example
```typescript
// When updating status, APPEND to history (never delete/modify)
const newHistoryEntry: StatusHistoryEntry = {
  status: "active",
  changedAt: Timestamp.now(),
  changedBy: currentUser.uid,
  changedByName: currentUser.displayName,
  previousStatus: truck.status,
  reason: "Annual inspection passed"
};

await updateDoc(truckRef, {
  status: "active",
  statusHistory: arrayUnion(newHistoryEntry),  // Append only!
  updatedAt: serverTimestamp()
});
```

### Rules
- ❌ **NEVER** delete entries from `statusHistory`
- ❌ **NEVER** modify existing entries
- ✅ **ONLY** append new entries using `arrayUnion()`
- ✅ Include `changedBy` for accountability
- ✅ Include `previousStatus` for easy auditing

### Entities Requiring statusHistory
- ✅ Trucks (status changes: active → maintenance → inactive)
- ✅ Subcontractors (status changes: pending → active → suspended)
- ✅ Assignments (status changes: active → completed → cancelled)
- ✅ Users (status changes: active → disabled)

### Task ID Format
- **Format:** `FM-YYYYMMDD-DEST-XXX`
- **Example:** `FM-20260214-SOCN-001`
- **Purpose:** Ensure easy sorting and searching in Firestore.

### SPX Mapping
- **Field:** `spxTripId`
- **Requirement:** Must be stored separately to facilitate cross-referencing with Shopee's system (Runsheet).

## 2. Driver App Standards (Flutter)

### Synchronization
- **Goal:** Ensure data is always synchronized between Mobile and Web.

### Offline First
- **Requirement:** The app must support basic data entry (e.g., job updates) even without internet connection at the Hub.
- **Mechanism:** Store actions locally and sync when online.

### Contract First Development
- **Workflow:** 
    1.  Draft Data Schema in `shared-docs` (e.g., Zod for Web, Dart class for Mobile).
    2.  Review field names (e.g., `weight`, `sealCode`) with the team.
    3.  Implement UI/Logic only after Schema approval.

### Edge Case Checklist
- **Testing:** Always ask: "What if the driver presses the wrong button?" or "What if the internet drops?".
- **Goal:** Robust error handling and professional UX.

## 3. Shared Documents (SSOT)

### Single Source of Truth
- **Location:** `shared-docs` folder.
- **Rule:** When Web (TypeScript) Schema changes, the Mobile (Dart) model must be updated immediately to match.

### Feature Requirements
- **Mandatory Photos:**
    - Proof of Delivery (POD) with signature.
    - Seal Code photo.
    - **Requirement:** Cannot complete the job without these photos.
- **FCM Tokens:**
    - Stored in User/Driver Profile.
