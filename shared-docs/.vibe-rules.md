### Key patterns to remember
- **Client → server:** onCall (server) + httpsCallable (client); never trust client for auth or validation.
- **UI text:** All user-visible strings via `t("key")` (web) or locale files (mobile); add EN + TH.
- **Dates in UI:** Pass `locale` to date-fns when language is Thai: `format(date, "PPP", { locale: th })`.
- **Collections:** Use `COLLECTIONS.*` from `@/lib/collections`, no raw strings.
- **Select inside Dialog (Radix):** `DialogOverlay` และ `DialogContent` ใช้ `z-[1001]` / `z-[1002]` (`components/ui/dialog.tsx`) แต่ `SelectContent` ดีฟอลต์ `z-[1000]` (`components/ui/select.tsx`) — เมนู Select ที่พอร์ทัลไป `body` จะอยู่ใต้ overlay ทำให้คลิกเลือกไม่ได้. แก้โดยใส่ `className="z-[1005]"` (หรือสูงกว่า content) และมักใช้ `position="popper"` บน `SelectContent` ใน dialog ที่มีปัญหา (ดู `hub-dialog.tsx`, `LineHaulTaskDialog.tsx`).

   ```tsx
   },
   ```

4. **Checklist before commit:**

## ☁️ Server Logic & Cloud Functions (MANDATORY)

> **⚠️ ALL new API routes and server-side logic MUST be implemented as Firebase Cloud Functions, not as Next.js API routes.**

### Rule
- **When the client invokes server logic:** Always use the **onCall + httpsCallable** pattern. Define the function with `onCall` in `logitrack-web/functions/src/` (e.g. `holidays.ts`), and call it from the web app with `httpsCallable(functions, "functionName")`. Do not perform sensitive or validated mutations by writing directly from the client to Firestore; use a callable function so auth and business logic run server-side. See `logitrack-web/docs/CALLABLE_FUNCTIONS.md` for the full pattern and holidays example.
- **New server logic:** Create callable or HTTP Cloud Functions in `logitrack-web/functions/src/`, export from `index.ts`, and deploy with `firebase deploy --only functions`.
- **Client usage:** Call them via `getFunctions()` + `httpsCallable(functions, "functionName")` from `@/firebase/client` (region `asia-southeast1`).
- **Do not add** new routes under `logitrack-web/app/api/` for business logic; reserve `app/api/` only for static redirects or legacy compatibility if needed.
- **Secrets:** Use Cloud Console environment variables or Firebase config for keys (e.g. `GOOGLE_MAPS_API_KEY`); never expose in client bundles.
- **Session revoke (Security Center):** Callable `revokeUserRefreshTokens` (admin only) calls `admin.auth().revokeRefreshTokens(targetUid)` and appends `security_events` with type `user_sessions_revoked`. Web: Security Center → Users → row menu “Revoke sessions”. Cannot target self from callable. Classic Firebase Auth does not expose a per-device session list; bulk “logout everyone” is intentionally not implemented.

### Rationale
- Single runtime for server logic (Firebase), easier scaling and monitoring.
- Secrets stay in Google Cloud, not in Next.js server env on Hosting.
- Aligns with existing auth, users, triggers, and distances functions.

### Checklist for new server-side features
- [ ] Implement in `logitrack-web/functions/src/<feature>.ts` (e.g. `distances.ts`, `users.ts`).
- [ ] Export from `functions/src/index.ts`.
- [ ] Call from web app via `httpsCallable(functions, "exportedName")`.
- [ ] Document required env/config (e.g. `GOOGLE_MAPS_API_KEY`) for deploy.

### 🗄️ Database Collections (MANDATORY)

> **⚠️ ALL collection names MUST use const variables. No string literals allowed.**

**Define collection names in a constants file:**
```typescript
// lib/collections.ts
export const COLLECTIONS = {
  USERS: "users",
  TRUCKS: "trucks",
  DRIVERS: "drivers",
  SUBCONTRACTORS: "subcontractors",
  ASSIGNMENTS: "assignments",

```

**Usage:**
```typescript
// ❌ WRONG - hardcoded string
const docRef = doc(db, "users", id);
const collRef = collection(db, "subcontractors");

// ✅ CORRECT - use const variable

const docRef = doc(db, COLLECTIONS.USERS, id);
const collRef = collection(db, COLLECTIONS.SUBCONTRACTORS);
```

**Benefits:**
- Typo prevention with TypeScript autocomplete
- Easy refactoring if collection names change
- Single source of truth for all collection names

## 🚦 Compliance & Thresholds (MANDATORY)

> **⚠️ All compliance logic MUST follow these standard thresholds.**

### Warning Levels
1. **Overdue (Red)**
   - Date: Past due (< 0 days)
   - Mileage: Over limit (< 0 km remaining)
   
2. **Due Soon / Expiring (Orange)**
   - Date: 0 - 30 days remaining
   - Mileage: 0 - 2,000 km remaining (User specified)

3. **Incoming (Blue)**
   - Date: 31 - 60 days remaining
   - Mileage: 2,001 - 5,000 km remaining

### Implementation Rule
- Use these constants in both **filtering logic** (List Pages) and **status calculation** (Cards/Widgets).
- Do not hardcode numbers like `1000` or `30` in multiple places; define them once or follow this standard strictly.

## 🚀 Deployment & Routing Standards (MANDATORY)

### Static Export vs Dynamic Routes
> **⚠️ CRITICAL: Firebase Hosting + Next.js Static Export Issue**

- **Problem**: Accessing dynamic routes (e.g., `/admin/trucks/[id]`) directly on Firebase Hosting often triggers a 404/redirect loop because the specific HTML file doesn't exist at the root level.
- **Solution**: Use **Query Parameters** for detail views that fetch data client-side.
  - ❌ **Avoid**: `router.push('/admin/trucks/' + id)`
  - ✅ **Use**: `router.push('/admin/trucks/view?id=' + id)`

### File Hygiene & Duplication
> **⚠️ NEVER leave duplicate or dead files in the codebase.**

- **Refactoring Rule**: If you move logic from `[id]/page.tsx` to `view/page.tsx`, you **MUST DELETE** the old `[id]` files immediately.
- **Why**: Having same-named components (`TruckPreviewClient`) in multiple locations causes:
  1. Build errors (Module resolution conflicts)
  2. Developer confusion (Editing the wrong file)
  3. "Ghost" bugs (Changes not reflecting)

## 📜 Immutable Logs Pattern (statusHistory)

> **⚠️ Status changes MUST be logged immutably for audit trail.**

### Implementation
```typescript
interface StatusHistoryEntry {
  status: string;           // The new status
  changedAt: Timestamp;     // When the change occurred
  changedBy: string;        // User ID who made the change
  changedByName?: string;   // Display name for convenience
  reason?: string;          // Optional reason for change
  previousStatus?: string;  // What it was before
}

interface EntityWithHistory {
  status: string;                    // Current status
  statusHistory: StatusHistoryEntry[]; // Immutable log (append-only)
}
```

### Usage Example
```typescript
// When updating status, APPEND to history (never delete/modify)
const newHistoryEntry: StatusHistoryEntry = {
  status: "active",
  changedAt: Timestamp.now(),
  changedBy: currentUser.uid,
  changedByName: currentUser.displayName,
  previousStatus: truck.status,
  reason: "Annual inspection passed"
};

await updateDoc(truckRef, {
  status: "active",
  statusHistory: arrayUnion(newHistoryEntry),  // Append only!
  updatedAt: serverTimestamp()
});
```

### Rules
- ❌ **NEVER** delete entries from `statusHistory`
- ❌ **NEVER** modify existing entries
- ✅ **ONLY** append new entries using `arrayUnion()`
- ✅ Include `changedBy` for accountability
- ✅ Include `previousStatus` for easy auditing

### Entities Requiring statusHistory
- ✅ Trucks (status changes: active → maintenance → inactive)
- ✅ Subcontractors (status changes: pending → active → suspended)
- ✅ Assignments (status changes: active → completed → cancelled)
- ✅ Users (status changes: active → disabled)

### 🔑 Google Sign-In Setup (Android - MANDATORY)

> **⚠️ Google Sign-In on Android requires ALL of the following to work correctly.**

#### 1. `google-services.json` (CRITICAL)
- **Location:** Must be at `android/app/google-services.json` (NOT in `android/app/src/`).
- **Requirements:** Must include BOTH:
  - `client_type: 1` (Android client with SHA-1 certificate hash)
  - `client_type: 3` (Web client for `serverClientId`)
- **How to get:** Firebase Console → Project Settings → Your apps → Android app → Download `google-services.json`.

#### 2. SHA-1 Fingerprint (CRITICAL)
- **Must be registered** in Firebase Console → Project Settings → Android app → Add Fingerprint.
- **Debug key command (PowerShell):**
  ```powershell
  keytool -list -v -keystore "$env:USERPROFILE\.android\debug.keystore" -alias androiddebugkey -storepass android -keypass android
  ```
- **Note:** `%USERPROFILE%` does NOT work in PowerShell. Use `$env:USERPROFILE`.
- **Without SHA-1:** Error `[16] Account reauth failed` will occur.

#### 3. Gradle Plugins (CRITICAL)
- **Project-level `android/build.gradle.kts`:**
  ```kotlin
  plugins {
      id("com.google.gms.google-services") version "4.4.4" apply false
  }
  ```
- **App-level `android/app/build.gradle.kts`:**
  ```kotlin
  plugins {
      id("com.android.application")
      id("kotlin-android")
      id("dev.flutter.flutter-gradle-plugin")
      id("com.google.gms.google-services")  // Add this
  }
  ```
- **No need** to add Firebase BoM to `dependencies` — Flutter handles Firebase SDKs via `pubspec.yaml`.

#### 4. `google_sign_in` v7.x API (CRITICAL)
- **Private constructor:** `GoogleSignIn` uses singleton pattern in v7.x. No unnamed constructor.
- **Correct usage:**
  ```dart
  // Initialize once with serverClientId from .env
  await GoogleSignIn.instance.initialize(
    serverClientId: dotenv.env['FIREBASE_WEB_CLIENT_ID'],
  );
  // Then authenticate
  final googleUser = await GoogleSignIn.instance.authenticate();
  ```
- **Guard against double-init:** `initialize()` must be called only once per app session.
  ```dart
  static bool _googleInitialized = false;
  if (!_googleInitialized) {
    await GoogleSignIn.instance.initialize(serverClientId: ...);
    _googleInitialized = true;
  }
  ```

#### 5. Firebase Duplicate-App Prevention
- When `google-services.json` + Gradle plugin auto-initializes Firebase AND `main.dart` also calls `Firebase.initializeApp()`, it causes `[core/duplicate-app]` crash.
- **Fix:** Wrap in try-catch:
  ```dart
  try {
    await Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform);
  } catch (e) {
    if (e.toString().contains('duplicate-app')) {
      Firebase.app(); // Use existing instance
    } else {
      rethrow;
    }
  }
  ```

#### 6. `.env` Configuration
- **Required key:** `FIREBASE_WEB_CLIENT_ID=xxx.apps.googleusercontent.com`
- **Where to find:** Firebase Console → Authentication → Sign-in method → Google → Web client ID.

#### Common Error Reference
| Error | Cause | Fix |
|-------|-------|-----|
| `clientConfigurationError, serverClientId must be provided on Android` | Missing `serverClientId` in `GoogleSignIn.initialize()` | Add `FIREBASE_WEB_CLIENT_ID` to `.env` and pass to `initialize()` |
| `[16] Account reauth failed` | SHA-1 fingerprint not registered in Firebase | Add debug SHA-1 to Firebase Console |
| `[core/duplicate-app]` | Firebase initialized twice (Gradle + code) | Wrap `initializeApp` in try-catch |

## 🗺️ Hub–SOC Distance (Google Distance Matrix)

### Purpose
- Compute **driving distance and duration** from each **Hub** to each **SOC** via Google Distance Matrix API and store in Firestore.
- **Use cases:** cost estimation (fuel/trip), maintenance cost estimation, future tire management (km tracking).

### Data
- **Collections:** `hub_soc_distances` (Hub→SOC), `soc_hub_distances` (SOC→Hub). Document ID: `{originId}_{destinationId}` via `hubSocDistanceDocId` / `socHubDistanceDocId` in `validate/hubSocDistanceSchema.ts` and `validate/socHubDistanceSchema.ts`.
- **Fields:** `hubId`, `socId`, optional **`network`** (`"SPX"` \| `"SPK"`) — กลุ่มที่ใช้จับคู่ตอนคำนวณ; `distanceMeters`, `distanceKm`, `durationSeconds`, `durationMinutes`, `hubLat`, `hubLng`, `socLat`, `socLng`, timestamps / audit fields ตาม schema.
- **Source:** Documents in `hubs` with coordinates. **Station type:** `station_type` `HUB` vs `SOC` (`RETURN_CENTER` ถือเป็น SOC). SOC ที่ `source_id` ขึ้นต้น `0` (stand by) ถูกข้ามตอนคำนวณ. **SOC ซ้ำ:** dedup ต่อกลุ่มด้วย `normalizeSocIdToKey(source_id)` (เช่น `SOCE` กับ `SOCE (…)` เป็นตัวเดียวกัน).
- **Network assignment:** `hubDistanceNetworkGroup(source_id, linkedCustomerCode)` ใน `validate/hubSchema.ts` — SPK จากรหัส hub หรือโค้ดลูกค้า J&T; นอกนั้น SPX เมื่อตรงกฎ `hubSourceIdHasSpxSuffix`.

### Usage policy
- **Run frequency:** Max **4 runs per month** to control cost (Hub list changes rarely).
- **Trigger:** On-demand button in Admin (e.g. Sources or First Mile): "Calculate Hub–SOC distances".

### Cost (167 Hub × 3 SOC)
- **501 elements** per full run; batched as **7 requests** (25 origins × 3 destinations per request).
- **4 runs/month** ≈ 2,004 elements → within **10,000 free/month** → **no charge**.
- Env: `GOOGLE_MAPS_API_KEY` (server-only). Enable **Distance Matrix API** in Google Cloud; set budget/quotas.

### Implementation notes
- **Cloud Function:** Logic runs in Firebase Cloud Function `computeHubSocDistances` (callable, region `asia-southeast1`). Call from web via `httpsCallable(functions, "computeHubSocDistances")`. Do not implement as Next.js API route.
- **Per-network batches:** คำนวณแยกกลุ่ม **SPX** และ **SPK** — แต่ละกลุ่มต้องมีอย่างน้อยหนึ่ง Hub และหนึ่ง SOC ที่มีพิกัดจึงจะได้คู่; ไม่ข้ามกลุ่มระหว่าง Shopee กับ J&T.
- **Shared core:** Pure helpers ใน `functions/src/core/distances.ts` (sync กับแนวคิดใน `validate/hubSchema.ts` / `hubSocDistances.ts`).
- Batch: 25 origins per request (max 100 elements). Optional short delay between requests for rate limit.
- Env: set `GOOGLE_MAPS_API_KEY` in Cloud Console (Functions config) or Firebase config.

  - [ ] **Phase 4 (ทางเลือก):** `public/robots.txt` (แก้ 404 จากสแกนถ้าต้องการ), `public/.well-known/security.txt` ช่องทางรายงานช่องโหว่

  - **การจัดการ Dashboard Maps**: แสดงผลรถยนต์พร้อม Popup ข้อมูล OdometerKm และรายละเอียด Fuel (ปริมาณ/เปอร์เซ็นต์) เป็น Real-time จาก Cartrack

    - **จัดการคนขับ (Driver & Assignments)**: ผูกข้อมูลคนขับเข้ากับ Subcontractor และจัดทำ Truck assignment จับคู่รถกับคนขับ

  - **Leave Request Admin**: อนุมัติการลา (Approve/Reject) ของคนขับ โดยตรวจสอบเอกสารแนบหลักฐานผ่านแผงควบคุมแอดมิน
  - **Accounting Audit (รายการเบิกจ่าย)**: ตรวจสอบและรับรองยอดเติมน้ำมัน/ซ่อมเร่งด่วน ที่คนขับส่งแนบเบิกบิลผ่าน Client-side
- **Rules & Patterns**:
  - **Compliance warnings**: กำหนดค่าแจ้งเตือน 30 วัน/2,000 กม. (สีแดง/Overdue) และ 60 วัน/5,000 กม. (สีเหลือง/Incoming)
  - **Admin i18n**: หน้า Dashboard หลักที่ระบุในตาราง "Admin i18n" ใช้ `t("key")` ผ่าน `context/locales/{en,th}/common.ts`; บางโมดูลใช้ไฟล์แยก เช่น `firstMile.ts`, `driverMonitor.ts`, `securityCenter.ts` — ตามโครงจริงใน repo
  - **Audit Logging**: บันทึกการอัพเดทสถานะลงใน `statusHistory` เสมอ เพื่อประวัติแบบ Immutable
  - **Driver Monitor Photo Slots (Admin)**: ใน `EditTripDetailsDialog` ต้อง render ช่องรูปตาม `TRIP_PHOTO_TYPE_ENUM` ครบทุกประเภทเสมอ (ไม่ผูกกับข้อมูลที่มีอยู่เท่านั้น) เพื่อให้แอดมินสามารถเพิ่มรูปใน step ที่ขาดได้; การบันทึกให้ merge/replace ตาม `type` ของรูปใน `trip_records.photos[]`.
  - **Accounting toll import (Admin)**: ใช้ `vehicle_expenses` collection เดิม (`type="other"`, `category="toll"`), ต้องผูก `truckId` ชัดเจนตอน import, และ default `status="PENDING"` เพื่อเข้า flow audit เดิม; หน้าอื่นอ่านข้อมูลผ่าน `actions.client.ts` เดียวกัน.
  - **Toll file parsing**: สำหรับไฟล์บัตร/ทางด่วน ให้ parse วันที่แบบ `dd/MM/yyyy HH:mm:ss` โดยเก็บเวลา, รองรับหัวคอลัมน์ไทย/อังกฤษ, และเพิ่ม fallback map คอลัมน์เมื่อ header เพี้ยน; ระวังคำค้นกว้างที่อาจชนกับหัว `วันที่เกิดรายการ`.

  - **Hub / SOC labeling (Admin)**: ใช้ `lib/hubDisplay.ts` + `buildHubCodeToDisplayMapFromHubRows` (หรือจาก entries) เพื่อแสดงต้นทาง/ปลายทางใน First Mile, Line Haul, และฟอร์มงาน; `resolveHubOrSocDisplay` รองรับรหัสดิบ, SOC หลัง normalize และ fallback จาก `SOC_DESTINATIONS`.

  - **Admin CRUD for rate entries**: `deleteCustomerRateEntry` และ `updateCustomerRateEntry` ใน `actions.client.ts` สำหรับจัดการ Rate Card รายตัว; ใช้ `DropdownMenu` แสดง Edit/Delete options ใน action column
  - **Date input format hints**: ไม่สามารถ override HTML date input display format ข้าม browser ได้ → ใส่ format hint ที่ label (เช่น `(dd/MM/yyyy)` / `(วว/ดด/ปปปป)`) ใน i18n keys

### Per-trip billing (Rate Card → `trip_records` snapshot)

**เป้าหมาย:** คำนวณ “ค่าเที่ยวประมาณการ” หลังส่งงานแล้วเขียนลง `trip_records` แบบถาวร (snapshot) เพื่อหน้า **Income / รายงาน** และลดการคำนวณซ้ำจาก client ที่อาจไม่ครบข้อมูล

**แหล่งข้อมูลใน Firestore**

| Collection | ค่าคงที่ | หน้าที่ |
|------------|----------|---------|
| `customer_rate_entries` | `COLLECTIONS.CUSTOMER_RATE_ENTRIES` | แถวอัตรา: `customerId`, `hubId`, `destinationCode`, `vehicleClass`, `rateThb`, `effectiveFrom`, `importId` ฯลฯ |
| `customer_fuel_rate_adjustments` | `COLLECTIONS.CUSTOMER_FUEL_RATE_ADJUSTMENTS` | กฎปรับเรทตามวันมีผล: `rateMultiplier`, `addThbPerTrip`, `effectiveFrom` |

**Logic คำนวณ (pure — ต้องซิงค์สองไฟล์)**  
- `logitrack-web/lib/billingCompute.ts` (web / tests)  
- `logitrack-web/functions/src/core/billingCompute.ts` (Cloud Functions)  
แก้อย่างใดอย่างหนึ่งต้องแก้อีกไฟล์ให้ตรงกัน

**ทำไมไม่ใช้ Firestore trigger** — โซน DB หลัก (`asia-southeast3`) และข้อจำกัดของ Gen1/Gen2 Eventarc ทำให้ทริกเกอร์อัตโนมัติเวลาเขียน `trip_records` ไม่เหมาะ / ใช้ไม่ได้ในคอมโบที่ต้องการ → เลือกใช้ **callable เรียกหลังส่งงาน + backfill จากแอดมิน**

**ลำดับการทำงาน**

1. คนขับยืนยันส่งงาน → Firestore `trip_records` ถูก merge `status: delivered`, `deliveredTimestamp`, ฯลฯ (`logitrack-mobile` — `delivery_trip_repository.dart`).
2. มือถือเรียก **`computeTripBillingSnapshot`** ส่ง `{ tripId }` — **best-effort** (`try/catch` กลืน error; การส่งงานยังสำเร็จแม้ billing ล้ม).
3. Cloud Function `logitrack-web/functions/src/tripBillingOnDelivered.ts`:
   - Region: **`asia-southeast1`**
   - **`enforceAppCheck: true`** — ถ้า App Check ไม่ผ่าน callable จะล้ม
   - **Idempotent:** ถ้า `trip_records.billingEstimateThb` เป็นตัวเลขอยู่แล้ว → ไม่คำนวณซ้ำ
4. โหลด `tasks/{taskId}` จาก `trip_records.taskId` แล้วสร้าง input คำนวณ:
   - **customerId สำหรับ billing:** `task.sourceHubLinkedCustomerId` ถ้ามี ไม่เช่นนั้น `task.destinationLinkedCustomerId` — ถ้าทั้งคู่ว่าง → ล้ม (ไม่ query rate)
   - **hub สำหรับจับคู่แถว rate:** `extractHubId(task.sourceHub)` (เอาท่อนก่อน `" - "` แล้ว normalize เป็นตัวพิมพ์ใหญ่)
   - **ปลายทาง:** `normalizeDestinationCode(task.destination)` (เช่น `SOCN…` → `SOCN`; รหัสอื่นคงรูปหลัง normalize)
   - **ประเภทรถ:** `task.truckType` ถ้าไม่มีใน logic จะใช้ default **`4WJ`**
   - **เวลาที่ใช้เลือกแถว rate / fuel:** `billDateMs` = `deliveredTimestamp` ของ trip ถ้ามี ไม่มีจึงใช้ `createdAt` ของ trip — เลือกแถว rate ที่ `effectiveFrom <= billDateMs` และใช้แถวที่ `effectiveFrom` **ล่าสุด**ที่ยังไม่เกินวันนั้น (เหมือนกันสำหรับ fuel adjustment)
5. จับคู่แถวใน `customer_rate_entries` แบบ AND ทุกข้อ: `customerId`, `hubId`, `destinationCode`, `vehicleClass`, และ `effectiveFrom` ไม่เกินวันคิด
6. นำ **base rate** จากแถวที่ match แล้วคูณ **rateMultiplier** และบวก **addThbPerTrip** จาก fuel rule ที่เลือกได้ (ถ้าไม่มี rule → multiplier = 1, add = 0); ปัดเป็นทศนิยม 2 ตำแหน่งตาม helper ใน `billingCompute`
7. `update` เอกสาร `trip_records` ด้วยฟิลด์ snapshot เช่น `billingEstimateThb`, `billingBaseRateThb`, `billingRateImportId`, `billingLookupHubId`, `billingLookupDestination`, `billingFuelAdjustmentId`, `billingRateMultiplier`, `billingAddThbPerTrip`, `billingEffectiveFromDateStr`, `billingCustomerId` (ค่านี้เป็นผลลัพธ์จากขั้นตอนคำนวณ ไม่ได้อ่านชื่อเดียวกันจากฟอร์ม task โดยตรง)

**Backfill และเว็บ**

- **Driver Monitor** (`useDriverMonitor.ts`): โหลดเที่ยวแล้วเติม snapshot ถ้ายังไม่มี (มีขีดจำกัดจำนวน task ใน memory ต่อรอบ)
- **Income (admin):** callable **`backfillTripBillingSnapshots`** — เฉพาะ admin, สแกน `trip_records` ตามช่วง `createdAt` (ปฏิทินกรุงเทพ), เติมเที่ยว `delivered` ที่ยังไม่มี `billingEstimateThb`

**เวลาแก้ “ไม่มี billing บน trip”**

- ตรวจ **เอกสาร task** จริง (ไม่ใช่แค่ `origin`/`destination` บน `trip_records` — function อ่านจาก `tasks` เท่านั้น)
- ตรวจแถว **`customer_rate_entries`** ให้ตรงทุกคีย์ + `effectiveFrom`
- ตรวจ **App Check** และว่า function deploy แล้ว
- ดู log ของ Function: เมื่อจับคู่ไม่ได้จะมี warn พร้อม `customerId`, `hubId`, `destination`, `vehicleClass`, `billDateMs`, `rateRowsForCustomer`, `rawTaskSourceHub`, `rawTaskDestination`

### Tab disable rules (MainLayout)

- **Pick up (Loading)** disabled when there is an active trip not yet delivered (`_savedTripSummary != null`). User must complete delivery first.
- **Delivery** disabled when no trip has been received yet (`_savedTripSummary == null`). User must record a pickup first.
- On successful delivery submit, `onDeliveryCompleted` clears the active trip so Pick up is enabled again.
