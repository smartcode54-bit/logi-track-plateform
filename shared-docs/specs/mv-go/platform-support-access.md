## 1. Problem & Goal (ทำไมต้องทำ)

A platform administrator needs to inspect a tenant without acquiring membership or tenant write privileges. The tenant must control whether that inspection reveals personal information and money, and must see the support visit and consent changes in its Security Center. Today `SwitchTenant` requires membership, while `X-Act-On-Tenant: <id>` acts as a writable tenant administrator (`logitrack-api/internal/auth/me.go:355`, `logitrack-api/internal/iam/authorize.go:35`). Neither is the required support session.

This is a proposed implementation, not an assertion that support mode or masking already exists. Source citations are repository-relative `file:line` anchors verified in this worktree on 2026-10-16. Owner requirements and final decisions below take precedence over older specifications. Only this spec and ADR 0030 are changed by this documentation task. Decisions and verified review dispositions are recorded in §3; only genuinely open owner questions appear in §9. The final revision dispositions below are binding decisions; Draft status concerns approval of the implementation design.

## 2. Scope

**Phase 1 (required before support entry is enabled):**

- Searchable company switcher modal, explicit read-only support entry/leave, persistent tenant consent toggle, visit/consent security events and session/cache coordination.
- Ship D1 header closure and D2 IAM restrictions as the **first release gate of Phase 1**, before support entry is enabled: close `X-Act-On-Tenant` for every human principal in every mode, restrict platform IAM writes, and replace every shipped header consumer with purpose-built platform endpoints (§4.3). Their tenant PII follows each **target tenant's own consent**, including platform-only sessions and the existing platform role `support`; that role does not gain support-session entry.
- Mask Dashboard and the **whole Fleet & partners category**: trucks, truck assignment, drivers, renewals, maintenance and partners. Include their lists/details/pickers, nested dependencies, exports, files, jobs, errors, caches and SSE; maintenance costs and partner identity documents are part of this phase.
- Keep full staff navigation visible. Every other tenant read route/endpoint in support mode returns `403 support_view_unavailable`; tenant mutations always return `403 support_read_only` first; the web renders localized “Not yet available in support view” without mounting its data loaders or returning unmasked data. Explicit session/consent controls and the enumerated pure platform controls in §4.3 are infrastructure exceptions, not permission to enable deferred tenant domains.

**Phase 2+:** Operations, billing/accounting, costs, HR, settings and security, one complete domain slice at a time (§6). The broad field inventory in §4.6 is the target contract, not a claim that all domains launch in Phase 1. Each later slice must pass projection, transport and refusal tests before its support allowlist entry is enabled. Tenant admins can use consent Settings and view security events in ordinary member mode from Phase 1; the visiting support user's general Settings/Security pages remain unavailable until their slices ship.

**Out of scope:**

- Impersonating another person, creating membership as part of entry, tenant writes in support mode, support entry for the existing platform role `support`, API keys, mobile or Firebase shims.
- Changing billing calculations/ownership, ordinary member access, mobile workflows or the current public evidence sharing contract. No consent expiry or support-visit idle timeout (D4/D5).
- Implementing the feature in this documentation task. Implementation later reconciles Appendix A/B/C and generated contracts; only these two documents are edited now.

## 3. Requirements

**Functional — requirements of 2026-10-15, refined by final decisions of 2026-10-16**

- **R1.** A user whose `platformRoles` contains `platform_admin` can enter **any** `own_fleet` or `carrier`, without membership, and see the full staff navigation. Phase 1 opens Dashboard and Fleet & partners; deferred destinations show the typed unavailable state (D3). Quarantine is never a support destination. The example addresses `kangana512@gmail.com` and `smartcode54@gmail.com` are examples, not an authorization allowlist. Current identity authority is the platform-role axis (`logitrack-api/internal/auth/issue.go:56`, `logitrack-web/features/auth/api/me.ts:199`).
- **R2.** Support sessions cannot create, edit, delete, assign, import, approve or otherwise change tenant data. Go must refuse the request before side effects. Existing platform administration remains available through its explicitly classified control routes; it cannot be used as an implicit tenant-write override (§4.3).
- **R3.** Each tenant's real `tenant_admin` may turn support access ON/OFF in Settings. OFF leaves menus, page structure, statuses, counts, dates and plates visible, but displays personal data and money as `****`. ON reveals authorized data on admitted routes, still read-only; it never reveals another tenant's personal data through the selected tenant's consent. A platform-granted tenant_admin cannot change consent until ratified, except the recorded first onboarding admin after its holder sets a self-chosen password; every platform-set credential blocks consent/ratification until that holder password change (§4.4). ON persists until a `tenant_admin` turns it OFF; there is no expiry, automatic approval or platform-admin consent override.
- **R4.** The header contains an active-company button opening a searchable modal. Platform administrators search all eligible tenants using pagination. Other users choose from their memberships. Extend/replace the existing switcher (`logitrack-web/components/tenant-switcher.tsx:26`).
- **R5.** Support entry, exit and consent ON/OFF are durable security events visible to that tenant. An audit failure must prevent entry or a consent change (`logitrack-api/internal/security/security.go:63` already provides transactional append).

### 4.2 Session model and API contract

**Proposed extension of `POST /v1/auth/tenant`**, through existing `POST /api/auth/tenant`. It remains an authenticated session operation, not a tenant-data write. Go returns the existing `{data:{accessToken,expiresIn}}`; the BFF keeps the token in `lt_at` and returns 204 as today (`logitrack-api/internal/auth/me.go:344`, `logitrack-web/lib/bff/authRoutes.ts:479`).

| Body | Semantics |
|---|---|
| `{ "tenantId": "<uuid>", "mode": "member" }` | Existing membership switch. Omitted mode means `member` for compatibility. Require a usable real membership; never silently turn this into an administrative session. |
| `{ "tenantId": "<uuid>", "mode": "support" }` | Require a live human web session and a current database `platform_admin` grant. Load the tenant by ID; allow own fleet/carriers in active, pending **or suspended** status because R1 says ANY. Never quarantine. No membership insertion or mutation. |
| `{ "mode": "leave" }` | Close the support visit and restore the saved real membership when still usable; otherwise `pickTenant(users.last_tenant_id)`/earliest usable membership, otherwise platform-only (`tid`/`rol` absent). No target tenant supplied. Already outside support is an idempotent no-op. |

Unknown fields/mode combinations are 422; unauthorized entry is 403; nonexistent/quarantine targets are the same 404. Support entry to a suspended tenant does not reactivate it or grant its ordinary members access. Ordinary suspension behavior remains `logitrack-api/internal/auth/issue.go:78`. No email comparison, auto-grant or `X-Act-On-Tenant` construction is part of this flow.

**Claims and server state.** Add `sm:"support"`, `rol:"support_readonly"`, `tid:<selected>`, `scv:<session context version>`, `sacv:<consent version>` to a support access token; retain `sub/sid/ver/amr/plt`. Use decimal strings for the two bigint versions. Clear `dsp/cs/drv` for this session. Ordinary tokens carry `scv` and no `sm/sacv`. `support_readonly` is valid only with `sm=support`, a tenant, a human session and platform_admin; it is not accepted by membership/grant APIs or added to `memberships.role`. Existing token shape and role validation are at `logitrack-api/internal/auth/token/token.go:35` and `logitrack-api/internal/auth/middleware.go:216`.

`sessions.active_tenant_id` remains the active context. Add `access_mode`, `context_version`, `support_return_tenant_id` (§4.4). Every context transition increments `context_version`; every request using **session-backed Go credentials** checks that version against PostgreSQL at admission, including an old **member** token. Thus new requests cannot replay a pre-entry writable token. A missing `scv` means version zero only for an unchanged legacy member session; retain pre-migration web/android/ios token behavior until its first context transition, and issue explicit versions on refresh. Compare mode, tenant, role and current platform grant as well as version; disagreement returns `401 token_expired`, `details.reason="claims_changed"`. Sessionless Firebase shim principals (`SessionID=0`, `amr=firebase`) keep their existing verification/authorization and response contracts; no lookup of a nonexistent session row. Machine credentials keep their existing separate authentication. Neither can enter or carry support mode. Do not cache a negative “not in support” result (`logitrack-api/internal/auth/middleware.go:138`, `internal/authz/principal.go:73`, `internal/auth/shim.go:73`, all under `logitrack-api/`).

Visit lifetime follows D4: no idle timeout or extra support-only cap; only leave, switch, logout, revocation/platform-role loss or normal session expiry ends it (§4.9).

Refresh rotates the same refresh family and reissues the current mode, context and consent versions. It must not call `pickTenant()` for a valid support context. Role removal ends that visit and returns the user to a real usable membership or platform-only context, with a new context version; disable/revocation signs out normally. `users.last_tenant_id` is updated only by normal member login/switch, never by support entry/refresh/exit. Entry from member mode saves its tenant once; support A → B retains that return target. This avoids teaching subsequent logins to open a non-member tenant (`logitrack-api/migrations/0025_user_last_tenant.sql:1`, `logitrack-api/internal/auth/refresh.go:24`).

Transition transaction: preserve the existing user → session row-lock order; reread role/target under authorization; close the previous visit if any; update session; append the new visit and events; sign the access token; commit. Identical mode/target retries return the current context without duplicate events. A → B writes `left` under A and `entered` under B, without naming the other company in either event. Refresh and consent changes do not count as new visits. The current switch uses a single system transaction and preserves refresh tokens (`logitrack-api/internal/auth/me.go:360`). **No per-session shared/exclusive advisory lock is required.** A member write admitted before transition was authorized by a real membership and may finish; subsequent requests must fail the live `scv` check. Where a write needs transaction-time freshness, reread `sessions.context_version` within that transaction using the established lock order; do not claim this cancels earlier authorized work. Existing queued work retains its original actor/authorization. This avoids threading a new lock through every write and plain query-handle job path (`logitrack-api/internal/jobs/http.go:184`).

**`GET /v1/me` additions:**

- `tenant`: selected tenant loaded by ID, with `role:"support_readonly"`; `tenants`: actual memberships only.
- `sessionContext`: `{mode:"member"|"support", version:"<scv>"}`.
- `supportAccess`: `null` outside support; otherwise `{tenantId, enabled, masked:!enabled, version:"<sacv>", readOnly:true, visitId}`. This is current server policy, never a client preference.
- `capabilities`: tenant/view permissions in the active context. `platformCapabilities`: the separately resolved existing platform set, for explicitly classified platform controls only. Normal sessions may retain the existing combined list for compatibility; support sessions may not.
- `dispatcher:false`, `customerScopes:[]`, `driver:null` in support. The caller's own account name/email in `/me` remains its own identity, not a tenant-data disclosure.

Update `MeDTO` and all parsers together; `parseMe` currently drops unknown fields (`logitrack-web/features/auth/api/me.ts:68`, `logitrack-web/features/auth/api/me.ts:110`). No token/refresh token enters JavaScript.

### 4.3 Capabilities, row reach and write refusal

**Phase admission.** Keep destination visibility separate from API capability grants. In Phase 1 only Dashboard, the six Fleet & partners destinations listed in §2, their explicitly registered dependencies/transports, session/consent infrastructure and enumerated pure platform controls are admitted. After classifying the explicit own-account/session and pure platform exceptions below, **every tenant mutation in support mode returns `403 support_read_only` first**, including mutations in deferred/unknown domains and side-effecting GETs. Deferred/unknown **reads** return `403 support_view_unavailable` in both consent states. This precedence applies before cache/idempotency lookup, data access or side effects; unknown non-read methods cannot become read exceptions. ON never overrides phase admission. The following read-key tables describe the eventual contract; add/enable deferred-domain keys only with that domain slice.

**Existing catalog read subset.** Derive support reads as an explicit allowlist intersected with `TenantDefaults(TenantAdmin)`, independent of tenant overrides, then apply route/data policy. Do not infer reads from a `view_` prefix, and do not use `PlatformCaps` union. The current catalog/defaults are `logitrack-api/internal/authz/catalog.go:34`, `logitrack-api/internal/authz/roles.go:58`.

| Domain | Existing keys included in the support read set |
|---|---|
| Fleet | `fleet:view_trucks`, `fleet:view_renewals`, `fleet:view_assignments`, `fleet:view_live_map` |
| People and communication | `drivers:view`, `drivers:view_pii`, `users:view`, `chat:view`, `broadcasts:view` |
| Operations | `operations:view_first_mile`, `operations:view_line_haul`, `operations:view_driver_monitor`, `operations:view_incidents` |
| Billing/accounting | `accounting:view_fuel`, `accounting:view_other`, `accounting:view_rate_card`, `accounting:view_income`, `accounting:billing_result`, `accounting:shopee_report` |
| Reporting/HR/company | `reporting:view_analytics`, `hr:view_payroll`, `hr:view_leave`, `company:view`, `packages:view` |
| Security tenant view pages (later slice) | `security:view_overview`, `security:view_audit`, `security:view_mobile_clients` |

`drivers:view_pii` permits the field's place in the response, not bypassing consent. `security:view_status` and `waitlist:view` belong to platform control reads, not the tenant support set. Selected-tenant consent never authorizes platform lead PII; return reviewed status DTOs and a waitlist **counts DTO** in support, in both consent states; no raw lead rows. Serialize admin-count/consent checks with membership/status/credential changes; a disable, delete, demotion or removal cannot first erase the admin and then claim onboarding. No/ambiguous target fails closed. All these tenant writes remain `support_read_only` in support regardless of ON/onboarding. Preserve independently authorized non-platform tenant-admin workflows and holder self-service recovery; a platform actor holding a member role cannot launder its actions through member mode.

**Credential eligibility.** Atomically stamp `credential_reset_by_platform_at` whenever a platform actor sets/replaces an account's credential, including initial onboarding credentials and temporary passwords; force `must_change_password` and use the existing credential/session invalidation path. Platform-initiated invite/reset flows retain their origin through token redemption; only the holder's actual self-chosen password submission records `credential_self_chosen_at`. Consent toggle and ratification recheck these fields in the transaction: a platform-set latest credential, pending must-change state or missing later self-chosen change denies both, even if consent is ON or a membership was previously ratified. Cached sessions/JWT eligibility cannot bypass this. A platform actor's administrative password change is never recorded as holder self-service. Use the existing must-change-password ticket flow (`logitrack-api/internal/auth/passwords.go:279`) and password-write transaction (`logitrack-api/internal/auth/passwords.go:396`) to record completion; merely logging in, enabling the account, redeeming an unchanged platform credential or clearing a flag is insufficient. Formally, credential eligibility requires `must_change_password=false` and either no platform-reset timestamp or `credential_self_chosen_at > credential_reset_by_platform_at`; a recorded first onboarding grant additionally requires a self-chosen completion after its creation. Legacy accounts with neither timestamp are not blocked solely by missing history. A later platform reset blocks authority again; it does not erase ratification history.

**Ratification and first onboarding admin.** Record `granted_by_platform`, grantor and time for every platform-originated membership grant, not only tenant_admin. Ordinarily, consent authority requires ratification by a distinct active eligible tenant_admin whose membership predates the grant. Except the decided first-admin bootstrap below, an unratified platform-granted membership cannot ratify itself or another grant; a platform-originated ratification cannot qualify. **Owner-decided first-admin exception:** the first tenant_admin created by a platform admin during initial onboarding becomes eligible to toggle and ratify later grants only after its holder sets a self-chosen password through must-change-password. Retain `granted_by_platform=true`; record this eligibility basis explicitly, without inventing a self-ratification or turning consent ON. Proposed `POST /v1/tenants/:id/members/:userId/ratify` takes `{expectedGrantVersion:"<decimal>"}`. Stale grant/provenance is `409 membership_grant_changed`; ineligible/platform/self-ratification is `403 ratification_not_allowed`, with no partial update.

**Ratification read model.** Extend ordinary member DTOs from `GET /v1/tenants/:id/members` (and projected platform member DTOs) with `grantedByPlatform`, `ratifiedAt`, `grantVersion`, `eligibilityBasis` (`member`, `ratified`, `first_admin_self_chosen`, `pending`) and viewer-relative `eligibleToRatify`. **Migration decision and review procedure.** Existing memberships with no attributable platform-actor evidence migrate as `granted_by_platform=false`; missing evidence alone never strands every tenant OFF. Every successful D2 platform action (including disable/enable/delete/demote/remove/driver-link as well as grant/raise/invite/reset/temporary password) appends a tenant-visible event with real actor, target user, action, onboarding/consent basis and outcome, and durably notifies **all pre-operation existing active tenant_admins** in each affected tenant. Snapshot recipients before removal/deletion; deduplicate retries. Passwords, tokens and sensitive snapshots never enter events/outbox. Audit/outbox failure rolls back the operation. Existing grant protections and `notSelf` remain; allowed credential/account operations never themselves ratify or toggle consent.

Use optimistic concurrency: a stale expectedVersion returns `409 support_access_changed` with current version, no input echo; repeating the same enabled value/current version is a no-op. A real change atomically updates the boolean, increments the version, records actor/time, appends `support_access_enabled` or `support_access_disabled`, and writes realtime outbox `tenant.support_access_changed {tenantId,enabled,version}`. No expiry job. ### 4.5 Mandatory server projection and live consent

**Mechanism.** Add a transport-neutral policy context and projector in `internal/platform/httpx` (no `httpx → authz` import cycle). IAM installs policy into request context; `httpx.JSON`, `Page` and `WriteError` consume it. Domain packages register complete response schemas: each exported JSON field is `safe`, `person`, `money`, `address`, `file`, `free_text`, `secret`, or recursively classified. Embedded structs, arrays, maps, metadata and `json.RawMessage` are covered. Tagging a parent `nested` requires a complete child schema; no untyped pass-through. This builds on the centralized envelope (`logitrack-api/internal/platform/httpx/response.go:49`) and the existing separate domain DTOs (`logitrack-api/internal/drivers/read.go:47`, `logitrack-api/internal/hr/payroll.go:48`).

Use explicit per-domain projections for raw JSON and sensitive joins. An outer response-admission guard requires proof of projection/schema coverage before any bytes are committed, including direct JSON/Send/redirect branches; streaming uses separately registered authorized adapters. `httpx.JSON/Page` alone cannot intercept all writes. Install the guard in both listener pipelines, encompassing final error handling as well as successful handlers. For buffered responses the projector produces a request-local, non-client-settable receipt bound to endpoint policy, audience/versions, schema, final status/headers and exact body bytes. After handlers/error serialization finish, the guard validates that receipt against the actual response; later body/header replacement invalidates it. On failure discard the response, Location and sensitive headers and emit only the known-safe `503 support_projection_unavailable` envelope. Empty/HEAD/error responses need their explicit safe receipt too. No tenant bytes are flushed while this decision is pending. This protects platform-projected responses in normal/platform-only modes as well as support.

Streaming cannot get admission from a flag on a raw writer. Register specific broker/SSE adapters with route, source domain, tenant resolver, content/header rules, current-version check and bounded-chunk revocation callback. The adapter receives a scoped permit immediately before first byte; unregistered SendStream/stream-writer/redirect/hijack paths are prohibited. P1.0 tests final guard ordering with Fiber's buffered responses and error handler; P1.4 tests actual first-byte and mid-stream behavior on both listeners. Ordinary/public transports retain their own existing contracts.

CI must **discover**, not merely iterate a hand-maintained DTO inventory: use Go package/type analysis of mounted handler call graphs, serialization/writer call sites, inferred concrete generic/interface response types and domain return types. Compare discovered JSON-visible fields (including embedded promotions and `omitempty` fields absent from fixtures), map key/value schemas, nested elements, metadata and raw JSON against classifications. An unresolved interface/dynamic branch is unclassified until it uses a typed registered projection. Discover direct `c.JSON`, `Send`, redirect, stream and raw fasthttp writers, with a narrow adapter allowlist; classify outside generated sqlc files. Negative fixtures independently add an unclassified nested/omitted field, a newly returned DTO and a direct writer to a mounted route **without updating the test inventory**: analyzer CI must fail, and runtime admission must refuse any such response if it reaches the server. Use the common writer for final validation/masking, not a regex over field names or serialized JSON. Classify by meaning: `name` can be an organization, a person, or user-authored content. Mask a copy so cached objects used by members are never mutated. ON still runs classification and secret stripping; it is not permission to dump SQL rows.

## 8. Risks & rollback

| Risk | Mitigation / accepted boundary |
|---|---|
| Alternate human header or platform IAM bypass defeats consent | D1 removes header reach/tenant-write override in every human mode; D2 guards all tenant_admin account/membership actions transactionally, counts disabled admins, retains provenance/credential origin, requires holder self-chosen credentials plus ratification or first-admin eligibility, and notifies admins. Platform controls are not blanket tenant authorization. |
| **Pre-existing spec gap: customer-scope accounts created or granted by platform actors are not consent-gated** | Close this gap or record explicit owner acceptance before enabling the support-entry gate. |
| Platform/global reads disclose B using A's consent or no tenant | Resolve target ownership per row/join, apply target consent in every platform mode, mask unowned/global PII, use exact tenant predicates and `Steward=false` in support. |
| New DTO/raw writer/file/export bypasses masking | Projection proof at outer response admission, recursive schema/writer discovery, transport adapters and negative fixtures; deferred domains fail closed. |
| OFF leaves old tokens/cache/SSE/URLs usable | Authoritative version checks, final delivery recheck, authenticated brokers, identifier-only events and audience eviction; never rely on TTL alone. Already delivered data cannot be recalled. |
| Old member token or direct upload survives entry | Session-backed credentials check `scv` at admission; earlier legitimately admitted member work may finish. Context-bound web upload broker plus drain of old PUT grants. Preserve sessionless shim compatibility; no fictitious session row. |
| **Accepted D4: forgotten support tab stays active** | No idle timeout/additional support cap by owner choice. Visit remains until actual leave/switch/logout/revocation/session expiry; retain entry/leave events, visible banner and prompt consent revocation checks. |
| **Accepted D5: independently held public evidence links** | Existing anonymous sharing contract remains, including non-expiring links where configured. A platform actor holding a link independently may use it outside support. Support never receives/mints public evidence URLs/tokens; do not claim consent revokes those links. |
| **Accepted D5: financial inference from visible data** | Liters × public fuel price can estimate a masked fuel amount; payroll category/quantity × an independently known rate can estimate pay; distances/trip counts × known tariffs can estimate revenue/cost. Dates/status/counts/plates and other approved non-money values remain visible. Mask direct money/rates/totals and sensitive predicates; no claim of eliminating external inference. Later slices inherit this risk acceptance. |
| **Accepted for gate 1: quarantine review rows are unprojected global data used for platform maintenance** | This is an accepted exception for gate 1. Project the rows before enabling the support-entry gate. |
| **Accepted visibility/linkability of dates and identifiers** | The owner retains dates, including driver birth date, plus stable IDs/plates/status/counts. These can identify/link records or reveal activity with outside knowledge. Apply exact reach and person-field masking; do not describe the result as anonymization. |
| Permanent consent or partial coverage misunderstood | Explicit ON-until-OFF copy, read-only banner and localized deferred-domain state. Full navigation does not claim every page is available in Phase 1. Carrier billing remains truthful unavailable/empty. |
| Initial onboarding / credential provenance | The first platform-created tenant_admin becomes eligible only after its holder sets a self-chosen password; consent stays OFF until explicitly changed. Other evidenced grants need the tenant's own eligible ratifier. No-evidence pre-existing memberships use the decided false migration default; no platform review override. |
| **Accepted pending-partner KYC limitation** | With consent OFF and no eligible tenant admin, partner ID cards/documents remain masked/unavailable even on platform onboarding/KYC routes. Platform reviews the documents **out of band**; no in-product consent or projection bypass. This operational delay/external review requirement is an owner decision, not an open question. |
| Partial rollout/old replica parses or serves data unsafely | Default-OFF entry feature gate and additive migration; D1/D2 ship first as one API/BFF/client release unit closing live holes, then complete Phase 1 API/web/transports reach every replica before entry. Per-domain allowlist gates later slices; no unmasked fallback and no support traffic to old replicas. |

Rollback disables new entry, closes support visits/increments contexts, returns affected sessions to member/platform-only mode and clears caches before reverting feature code. Retain consent, provenance/ratification, visits and audit history. **D1 header closure, D2 IAM restrictions and target-tenant projection remain deployed**; never roll back to the old inspector or unrestricted reset path. A later-domain rollback removes its allowlist entries and restores `support_view_unavailable`, without disabling already verified domains. Do not remove schema while any accepted credential depends on it.
