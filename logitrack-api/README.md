## Listeners (main spec §2.6)

| Listener | Env | Serves |
|---|---|---|
| internal | `API_INTERNAL_ADDR` | every route group, incl. `/readyz`, `/startupz` |
| public | `API_PUBLIC_ADDR` | only groups marked public **and** listed in `PUBLIC_ROUTE_GROUPS` (subset of `/v1/mobile`, `/v1/auth`, `/public/v1`, `/evidence`, `/media`, `/healthz`); everything else `404 not_found` |
| metrics | `METRICS_ADDR` | `GET /metrics` (Prometheus), private |

`api routes` builds the API through the same `newAPI` as serving (`cmd/api/main.go`; domain groups are added there), refuses a group marked public outside the list and any public route other than `/healthz` or a path below `/v1/mobile/`, `/v1/auth/`, `/public/v1/`, `/evidence/`, `/media/` (`/media`: the owner-approved widening of 2026-10-10 for the local storage backend, T11) (exit 1; serving refuses the same at startup), and prints one line per route with the listeners that may serve it. A middleware or sub-app registered with `Use` is listed as `USE PATH` and matches every path below it, so on the public listener it is allowed only at or below `/v1/mobile`, `/v1/auth`, `/public/v1`, `/evidence` or `/media`, never at or below `/healthz`. The listener-wide middleware (`Use` at `/`, `newFiber`) is not a route and no route check sees what it serves: never add a path-dispatching one (pprof, expvar, static files, a proxy); `TestRootMiddlewareIsPinned` pins its size. `go generate` writes it to `api/routes.txt`, so a route or listener change shows up in review and `make gen-check` fails when the table is stale.

`X-Forwarded-For` is honoured only when the TCP peer is inside `TRUSTED_PROXY_CIDRS`; the header is walked right to left and the first untrusted hop is the client. `X-Act-On-Tenant` is refused on the public listener (`400 header_not_allowed`).

Errors are always `{"error":{"code","message","details","requestId"}}` and `requestId` equals the `X-Request-Id` response header. Success bodies are `{"data": ...}`. JSON is camelCase.

## Lifecycle

`SIGTERM` → `/readyz` answers `503 unavailable` (`details.reason=draining`) → after a grace of `min(5s, SHUTDOWN_TIMEOUT/3)` every SSE stream gets `event: reconnect` `{"reason":"shutdown"}` and closes (`API.OnDrain`), both listeners stop accepting and in-flight requests drain within the rest of `SHUTDOWN_TIMEOUT` → exit 0. `/healthz` stays 200 until the listener closes.

Exit codes: `0` ok, `1` runtime error, `2` configuration error, `3` not implemented yet.

## Migrations (T03, main spec §3.5)

goose v3.28 runs the files of `migrations/` (embedded into the binary, so the `make migrate*` targets rebuild the image first) as `logitrack_migrator` through `MIGRATE_DATABASE_URL`; `migrate` refuses any other login, and `0001_preamble` repeats the check inside the database, where a refusal rolls the whole file back (R66). A session advisory lock serialises concurrent runs. goose creates `goose_db_version` before the first migration, owned by the login that runs it: if goose was ever run by hand with another login, drop that table before `make migrate`.

| Command | What it does |
|---|---|
| `make migrate` | `migrate up`: every pending migration (local, CI and seeded databases) |
| `make migrate-up-to V=9` | stop at a version; production stays at `up-to 9` (plus `apply 11`) until the P1 runbook applies `0010_d5_unique_constraints` (R59, R88) |
| `make migrate-apply V=11` | apply exactly one version ahead of the held `0010` (`migrate.Held`); a no-op once applied, refused while any other lower version is pending. Production P0 runs `up-to 9` then `apply 11` (the T11 storage column); the P1 runbook's `up` applies `0010` out of order, the only gap goose is allowed to fill |
| `make migrate-status` | every migration with `applied` / `pending`; `migrate status -fail-on-pending` exits 1 |
| `make migrate-down` | one step back; `down` and `down-to` are refused when `APP_ENV=prod` |
| `make migrate-new NAME=add_x` | writes the next `NNNN_add_x.sql` on the host |
| `make migrate-check` | the R31 rules, no database |
| `make migrate-roundtrip` | up → down-to floor → up on `postgres:18-alpine`, comparing `pg_dump --schema-only` |

Rules (`migrate check`, also part of `make gen-check`): files `NNNN_name.sql` numbered 1..N without gaps; every file has `-- +goose Up` and `-- +goose Down`; an empty Down only in a data migration whose header (before `-- +goose Up`) says `-- irreversible` (the round trip then rolls back only to the highest such version); `-- +goose NO TRANSACTION` exactly when the Up or Down builds or drops an index `CONCURRENTLY`; no empty `StatementBegin` block (goose would silently drop the next statement); ids default to `uuidv7()`, never `gen_random_uuid()`; no goose `ENVSUB`. Comments, strings and quoted identifiers are ignored when matching. Once a migration is applied to a database that is kept (from the P0 deploy on), it is never edited: follow-ups take the next number. Before P0 the baseline may still be corrected in place; goose records versions only (no checksum), so `make migrate` does not re-run an edited file on a database that already applied it, and such a local or dev database is reset (`make reset`).

**Upgrading an existing dev database (T10):** `0009_infra` now also grants `DELETE` on `jobs` to `logitrack_app` (the nightly `jobs.prune`). Baseline (T04): `0001`-`0009` are Appendix A §A.2.0-§A.2.8 with each file's Appendix C policy block (RLS on exactly the 70 tables of Appendix C §C.3.0, generators from 0001), `0009_infra` is the only file of the baseline that grants or revokes (R66) and hands the eight SECURITY DEFINER functions to `logitrack_rls_definer` (`0013` hands over two more, T23, with exactly the grants they need; `0014` two more, T27); `0010_d5_unique_constraints` (`NO TRANSACTION`) builds the three D5 unique indexes `CONCURRENTLY` and stops with an INVALID-index error while a legacy duplicate survives (R88). ## Auth (T05, main spec §4, Appendix C §C.4-§C.5)

Go returns tokens in JSON bodies and never sets cookies (the BFF does, TW3). Routes: `/v1/auth/{login,google/nonce,google,refresh,logout,logout-all,tenant,password/forgot,password/reset,password/change,sse-ticket}` on both listeners and `/v1/me`, `/v1/me/tenants`, `/v1/me/sessions[/{sid}]`, `PUT /v1/me/devices` and `DELETE /v1/me/devices/{installId}` (T13: one FCM token per user and install, at most 10 rows per user; a mobile session registers its own install only; the token moves from the caller's own rows, or from another user's row of the same install with a `device_token_moved` security event, else `409 already_exists`) on the internal listener only; `app.BuildAPI` hands the auth service to `newAPI` (`cmd/api`), so `api/routes.txt` lists these routes and serving checks them like every other group.

- **Access JWT**: EdDSA, `kid` = RFC 7638 thumbprint, claims exactly `iss sub aud exp nbf iat jti sid ver tid rol plt dsp drv cs amr` (empty optional claims omitted). `GET /.well-known/jwks.json` (internal listener only, TW3; `404 not_found` on the public one) serves `token.KeySet.JWKS`: the bare RFC 7517 document (no `{"data"}` envelope), active key first and, during a rotation, the `JWT_PREVIOUS_KEY_FILE` key, `Cache-Control: public, max-age=300`. The web edge gate verifies `lt_at` against it.
- **Per request** (`auth.Service.RequireAuth`): signature, iss, aud, exp (30 s leeway), then one Redis pipeline (`auth:sess:revoked:{sid}`, `auth:user:ver:{sub}`, bounded to 300 ms); a version miss or a token newer than the cached version reads `users.auth_version` and `sessions.revoked_at` and rebuilds both keys; with Redis down the same check runs in PostgreSQL (`auth_revocation_fallback_total`). Revoked session -> `401 session_revoked`; stale `ver` -> `401 token_expired` `details.reason=claims_changed`; expired -> `reason=expired`.
- **Sessions and refresh families**: one session per login (`active_tenant_id`, `install_id`; a re-login on the same install revokes the older one), refresh tokens rotate in a family; a rotated token presented within 30 s while its successor is unused yields a sibling, any other reuse revokes the family and session, bumps `auth_version` and writes `refresh_token_reuse` in the same transaction.
- **Revocation** (`auth.Service.RevokeInTx` + `Apply`): claims changes bump `auth_version` only; disable, password events, admin revoke, logout and reuse end sessions; every one queues outbox `user.sessions_revoked` on `user:{uid}` and, after COMMIT, raises `auth:user:ver:*` (only upward) and marks `auth:sess:revoked:*`; a failed write is retried in the background until the access tokens it judges expire (`auth_postcommit_failures_total{op}`; `Service.Close` stops the retries). `internal/iam` (T19) calls it for user administration and appends its row with `security.Append`. Lock order: every auth transaction that writes sessions or refresh tokens locks the `users` row first, then `sessions`, then `refresh_tokens`; `RevokeInTx` callers keep it.
- **Passwords**: Argon2id (parameters read back; weaker stored hashes re-hash on login), Firebase scrypt verify-then-rehash, `must_change_password` -> `403 password_change_required` with a single-use `passwordChangeTicket` redeemed at `/v1/auth/password/change`, forgot always `202` (outbox `auth.password_reset_requested`; the worker's `notify.email` consumer (T10) creates the token with `auth.IssueResetToken`, which stores only the hash), 5 failures / 15 min lock an email (`423 locked`; each attempt is counted before its check). Every failed check costs one Argon2id plus, while `FIREBASE_SCRYPT_*` is set, one scrypt (no timing enumeration); at most `GOMAXPROCS / ARGON2_PARALLELISM` hashes run at once (`503` after 3 s); a login opens its session only while the row still holds the credential it verified, so a racing reset wins.
- **Google sign-in** (T06, Appendix C §C.4.10): `GET /v1/auth/google/nonce` (web, through the BFF; single use, 10 min) and `POST /v1/auth/google {idToken, nonce?, platform, installId?, appVersion?}` with a GIS or `google_sign_in` ID token; no authorization-code flow (R23). `internal/auth/google` verifies with go-oidc (discovery on the first sign-in, so the api starts without Google; RS256; every `aud` in `GOOGLE_OIDC_ALLOWED_CLIENT_IDS`; `email_verified`). The account is the `auth_identities` Google `sub`, else the user with the verified email when Google is authoritative for it (a Gmail address or a Workspace account with `hd`), linked in the same transaction as `google_identity_linked`; otherwise `403 no_account` (no self-signup). A body nonce must be the token's and unused; a driver-app token (`azp` != `aud`) sent without one may carry the SDK's own nonce (iOS), which is ignored. Bad token or nonce `401 invalid_token`, Google unreachable `503`, variable unset `404`. Locally the variable is empty, so Google sign-in is off; tests use `googletest` (no network).
- Every statement runs in `db.WithSystem` (`app.bypass_tenant=on`); queries are sqlc (`internal/auth/queries` -> `internal/auth/authdb`). Tests: `go test ./internal/auth/... ./internal/security/...` (unit: JWT, the firebase/scrypt public vectors, Argon2id and the hashing gate, policy, equal work per failed check) and `make test-integration` (PostgreSQL 18 + Redis 7 containers, both listeners; `hardening_integration_test.go` covers the races and lost Redis writes).

## Users and tenants administration (T19, main spec §4, Appendix B §B.2.4-§B.2.5, Appendix C §C.8)

PostgreSQL is the users writer from P0 (R49). `internal/iam` `Admin` serves, on the internal listener behind `auth.RequireAuth` and the capability guard of each row: `GET|POST /v1/users`, `GET|PATCH /v1/users/{id}`, `POST /v1/users/{id}/invite|disable|enable|password/temporary`, `GET|DELETE /v1/users/{id}/sessions[/{sid}]`, `PUT|DELETE /v1/users/{id}/scopes/{customer|dispatcher}`, `PUT|DELETE /v1/users/{id}/driver-link`, `POST /v1/users/{id}/platform-roles`, `DELETE /v1/users/{id}/platform-roles/{role}`, `GET /v1/tenants/{id}/members`, `PUT|DELETE /v1/tenants/{id}/members/{userId}`, and (owner addition: multi-tenant from the first release) `GET|POST /v1/tenants`, `GET|PATCH /v1/tenants/{id}`.

- **One transaction per write** (`db.WithSystem` after Go authorization): the rows; `auth.RevokeInTx` (`claims_changed`: role, scope, driver link, platform role, email; the user's sessions stay and refresh, R50), `auth.SetStatusInTx` (disable / enable) or `auth.SetTemporaryPasswordInTx` (sessions end); the Firebase mirror before COMMIT while the bridge mirrors (`MirrorNewUserInTx`, `MirrorEmailInTx`); exactly one `security_events` row of Appendix C §C.4.13 (`user_created`, `user_updated`, `user_invited`, `user_role_changed`, `user_scope_changed`, `user_disabled`, `user_enabled`, `user_password_temporary_issued`, `user_sessions_revoked`, `driver_linked`, `driver_unlinked`, `platform_role_granted`, `platform_role_revoked`, `tenant_created`, `tenant_updated` (+ `tenant_contractor_changed`)); outbox `user.created` / `user.invited` (notify.email: invite = reset link, R29) and `tenant.created` / `tenant.updated`; `auth.Apply` after COMMIT. A request that changes nothing writes nothing.
- **Reach**: identity tables are platform-only under RLS, so the SQL names the reach: under `X-Act-On-Tenant: *` everyone; otherwise members of the request's tenant reach (contractor reach included) and, for a steward, accounts without a membership or platform role (customer-scope accounts, imported accounts still without a role). Outside it a user is `404`. `platform_admin` writes everywhere without the header; its reads of other tenants carry it (one `platform_cross_tenant_access` row each). ## API keys (T32K, slice of T32 #52 pulled forward; Appendix B §B.2.6, Appendix C §C.4.11)

Machine principals for scripts, integrations, `cmd/release` (T52) and, from M2, the Cloud Functions shims (T32). `internal/iam` `APIKeys` serves on the internal listener behind `security:manage_api_keys`, for people only: `GET /v1/api-keys` (keyset page, never the secret or its hash), `POST /v1/api-keys` (`{name, scope, capabilities[], expiresAt?, tenantId?}` -> `201` with the secret `ltk_<prefix>_<43 base64url>` once, `Cache-Control: no-store`; stored as `sha256(secret ‖ API_KEY_PEPPER)` by `internal/auth/apikey`; `api_key_created` in the transaction) and `DELETE /v1/api-keys/{id}` (`204`, `api_key_revoked` in the transaction, a second revoke is a no-op).

- **Rules**: `scope` is one of the CHECK list `integration`, `script`, `cf_shim`, `release_publisher` (else `422`); a tenant key holds tenant-class keys of the caller's effective tenant that the caller holds itself; platform keys (`tenantId` null) are created by `platform_admin` only and hold global-class and `mobile:*` keys; `cf_shim` is a platform key of `mobile:*` keys, `release_publisher` a platform key of exactly `security:manage_mobile_release`; never `platform:*` or `dispatch:*`. A pending or suspended tenant gets no key (`409`).
- **Per request** (`auth.Service.RequireAuth`): `X-Api-Key` is looked up by prefix in PostgreSQL on every request (no cache), so a revoked or expired key, or one of a tenant that is no longer active, is `401 invalid_token` (`details.reason` `revoked`, `expired`, `tenant_inactive`) from the next request; an unknown or wrong secret is `401` without details; a key with an `Authorization` header is `401` (`multiple_credentials`); then the key's bucket `rl:apikey:{id}` at `api_keys.rate_per_min` (`429`, `Retry-After`; on the shim targets a `cf_shim` key is charged only after the Firebase ID token passed, see "Callable shims"). `last_used_at` is written in the background at most once a minute per key.
- **Scope routing (R82)**: a route admits keys only when it is registered with `RequireAuth(auth.AllowAPIKeys(scopes...))`, and only on the internal listener; elsewhere a key is `403 permission_denied` (`details.reason = api_key_scope`). `POST /v1/auth/logout` and `POST /v1/auth/password/change`, which authenticate their caller themselves, refuse a key the same way (`auth.Service.refuseAPIKeys`) instead of acting as the bearer's user; anonymous routes ignore the header. Today `GET /v1/roles` admits `integration` and `script` keys (the role matrix and the other Security Center routes of T51 admit people only); `release_publisher` keys reach exactly the two APK publish routes `POST /v1/app-releases/presign` and `POST /v1/app-releases` (T52S); `cf_shim` keys reach only the callable shim targets of the public listener, together with a Firebase ID token (`auth.RequireShim`, see "Callable shims"); everywhere else they are refused like any other key. A machine principal holds exactly its key's capabilities (`authz.Effective`), acts in RLS as role `user` of its tenant or as a steward without a tenant for a platform key, and never takes `X-Act-On-Tenant`.

## Callable shims (T32R, rest of T32 #52; main spec §11.10, Appendix B §B.2.21-§B.2.22, Appendix C §C.6.5; R45)

The shims have no routes of their own.

| Callable | Target | Guard | Answer the shim rebuilds |
|---|---|---|---|
| `setDriverClaims` | `GET /v1/mobile/me` (`auth.Service.HandleMobileMe`) | `auth.RequireShim` | `GET /v1/me` plus `driver{id, tenantId, legacyDocId}` (`legacyDocId` = the Firestore drivers doc id, or the uuid of a driver created in Go); the shim merges `{role: 'driver', driverId: legacyDocId}` into the custom claims (Admin SDK, never overwriting other claims) and `users/{uid}.role`, and answers `{success, role, driverId, message}` as before; `403 no_account` / `driver_profile_required` or `driver: null` = "User is not a driver" |

| `computeTripBillingSnapshot` | `POST /v1/mobile/trips/{id}/billing/compute` (T38) | `auth.RequireShim`, `mobile:submit_trip` | `{ok, skipped?, error?}` |

- **Credentials** (`auth.RequireShim`): exactly one `X-Api-Key` of scope `cf_shim` (a platform key) and the caller's own Firebase ID token as `Authorization: Bearer`, verified against `https://securetoken.google.com/{FIREBASE_PROJECT_ID}` (audience `FIREBASE_PROJECT_ID`) in every `AUTH_FIREBASE_BRIDGE_MODE` (R45); the principal is the user's (AMR `firebase`, `driver:self` for a driver), the key its attribution. Missing either is `401 unauthenticated`, a revoked or unknown key or a rejected token `401 invalid_token`, a `cf_shim` key on the internal listener or on any other route `403 api_key_scope`. Without `FIREBASE_PROJECT_ID` the targets answer `404` (no `details.reason`; the `addDeliveryStop` shim logs it as an error instead of answering "Task not found").
- **Rate limits** (T32R): one platform `cf_shim` key serves every driver, so its bucket is not spent before the caller is known. `RequireShim` checks the key (secret, state, scope) and then the Firebase ID token without charging anything; an authenticated user is then charged to its own bucket `rl:shim_user:{key id}:{user id}` (60/min, Appendix B §B.6.3) and only then to the key's `rl:apikey:{id}` at `api_keys.rate_per_min`, which is the overall ceiling (the default 600/min: ten LogiTrack accounts would have to call at their own limit at once to reach it; `POST /v1/api-keys` takes no rate, so a platform operator raises it in PostgreSQL if the fleet's legitimate peak ever comes near). A caller Go refuses (bad or expired token, no account, a disabled account) spends nothing, and one user calling in a loop gets `429` (`details.bucket` `shim_user`) without touching the other drivers' calls.
- **Another driver's task** is resolved by `iam.TaskOwners` (a read-only system transaction: operations opens only principal transactions, the WithSystem allow-list) so it is `403 not_task_owner` and a missing one `404`; the write itself runs as the driver. In the write-back the same resolver reads the Firestore side of a partner-linked hub's carrier, whose tenant row is outside the driver's reach (`tenants.p_read`), so the stop names it as `addDeliveryStop` did.
- **Counter**: `shim_requests_total{callable}` (labels `setDriverClaims`, `addDeliveryStop`, `computeTripBillingSnapshot`, `markBroadcastRead`, created at 0 when the route is mounted) counts every authenticated shim request; with the Functions invocation metrics it is the retirement evidence (R26). The shim logs one `[shim] call` line per call with the HTTP status and duration (the latency evidence, AC < 300 ms p95) and an error line when Go refuses its credentials (a revoked `LOGITRACK_API_KEY`), fails (`5xx`, with `details.reason`), answers something that is not a Go envelope (a wrong `LOGITRACK_API_BASE_URL`) or cannot be reached; never the key or the token. `callShim` never follows a redirect (fetch would send `X-Api-Key` on to the other origin): a `3xx` is a failed call.
- **Functions params** (main spec §16.1): `LOGITRACK_API_BASE_URL` (the public API origin, `https://` only: a plain-http value other than localhost turns every shim off, since each call carries the key and an ID token) and `LOGITRACK_SHIM_CALLABLES` (the callables that forward; empty = every callable keeps its legacy path) in `FUNCTIONS_ENV_*`, `LOGITRACK_API_KEY` a Secret Manager secret. Deploying the Functions and creating the production `cf_shim` key are owner steps (main spec §19 question 18).
- **`addDeliveryStop` on a Firestore-owned deployment** (operations not in `PG_OWNED_DOMAINS`: P2 to P7b, where the shim goes live): the target needs T31's write-back (`WRITEBACK_FIRESTORE_PROJECT_ID`, `GOOGLE_APPLICATION_CREDENTIALS` with Cloud Datastore User; open hitl of #51) and the T29 mirror with its tasks listener (`worker-sync`, `ETL_SYNC_ENABLED`; hitl of #49/#44). Without the write-back it answers `503 write_back_unconfigured`, without the mirror a task created after the P1 load is `404 task_not_found`; the shim turns those into `internal` / `not-found`, and APK 3.x then submits the loading as a single-stop trip (the extra-stop billing is lost). So list `addDeliveryStop` in `LOGITRACK_SHIM_CALLABLES` only after a staff `POST /v1/tasks/{id}/stops` on a test task answers `200`/`202`; `setDriverClaims` needs neither and may go on first. The staging VM is PostgreSQL-owned for operations, so neither is needed there.

## Operations data layer (T27, issue #47; Appendix A §A.2.3, Appendix C §C.3.0)

`internal/operations` is the data access of the four operations collections, the base of the read APIs (T30), the write-back endpoints (T31), the mirror (T29), the realtime events (T33), the seed (T35) and the driver app routes (P7a). It adds no route; the DDL is `0004_operations` (T04), plus the two SECURITY DEFINER helpers of `0014_operations_seal_and_counter_helpers` (Appendix A §A.2.12, Appendix C §C.3.3).

- **Queries** (`queries/{tasks,trips,standby,incidents}.sql` -> `operationsdb`, sqlc block `operations` with `emit_interface`): every statement runs in the caller's transaction, so RLS decides (G-tenant; the driver's own rows, and for tasks the helper's, R28; the parent's reach for `task_delivery_stops`, `trip_delivery_stops`, `trip_photos`, `trip_no_history` (staff only), `standby_photos`). Staff lists and lookups also name the reach (`operations.Reach`: `authz.Principal.TenantReach`, a driver's id, or `SystemReach` for a system transaction; Appendix C §C.3.8). Lists are keyset pages (`created_at`, the task plan day, `delivered_at`, the billing axis day or `ended_at`, then `id`) with opaque cursors bound to their axis; no silent cap.
- **Task numbers (R10, AC):** `CreateTask` takes `next_task_seq(task_type, Bangkok plan day)` inside the insert transaction and formats `FM|LH-ddMMyyyy-NNN` (three digits, `-1000` past 999); the counter row stays locked until COMMIT, so concurrent creations of one type and day get distinct numbers across tenants, and a rolled-back creation leaves no gap. `logitrack_app` has no privilege on `task_number_counters`; the allocator is SECURITY DEFINER owned by `logitrack_rls_definer` (R66, R67). Runtime creates leave the number to the allocator; a number of record (a legacy or mirrored one, an unpadded `FM-01102026-7` included) is kept verbatim (`task_no` indexed, not unique; `TasksByNumber` returns every match), and a canonical padded one moves the counter of the day it names past it (`bump_task_seq()`), so the allocator never mints it again. An assigned task without a position gets `max(run_order) + 1` under the per-driver transaction advisory lock `LockDriverQueue`, which every `run_order` writer takes (developer-spec.md §3.6). Planned stops make a task multi-drop and need two or more.
- **Trip identity (AC):** `trip_no` UNIQUE and mutable; `tripcheck.ValidateTripNo` ports `core/tripDocId.ts` (the same rule as the column's CHECK; `internal/operations/tripcheck` is the one Go copy, the ETL uses it too). `RenameTrip` updates the number in place with one append-only `trip_no_history` row (delivered trips only, `409 failed_precondition not_delivered`; a held number `409 duplicate_trip_id`); `TripByNo` falls back to the most recent pre-rename number.
- **Photos (R19, AC):** `PutTripPhoto` merges by type (last wins) and accepts any non-empty type; `photo_type_known` (STORED) is true for the 14 workflow types and `stop_{n}_{arrived|pre_open|opening|empty_container|runsheet_received}`, `tripcheck.PhotoTypeKnown` is its Go twin, `UnknownTripPhotos` lists the rest; reads sort by the ADR 0018 rank (`PhotoRank`, port of `trip_photo_order.dart`).
- **Duplicate seal:** `CheckSeal` (the submit of `POST /v1/mobile/trips`, `409 duplicate_seal`) asks the SECURITY DEFINER `trip_seal_taken()` whether any trip in any tenant and status carries the seal, as the legacy query read every trip although a driver's RLS shows only its own; it takes a per-seal lock until COMMIT, so concurrent submits of one seal serialise, and the 409 names the holder only when the caller reaches it.
- **Stops and replays:** `AddTaskStop` ports `addDeliveryStop` (stop 1 = the task's destination, `409 duplicate_destination` on a trimmed upper-case match); driver-created tasks, standby records and incidents with a `client_op_id` are idempotent per `(driver_id, client_op_id)` (R63): a replay returns the stored row and allocates no number.
- **Standby billing (Appendix C §C.3.4, R61):** reads return the tenant owning the `standby_rate_entries` row a record names; `operations.Project` keeps the `billing_*` columns only for that tenant's staff, for the own fleet when the record names no rate entry (unpriced, a service-fee price, a legacy rate not linked yet: a service fee is never resolved through today's fee table, which may have changed hands), everything under `X-Act-On-Tenant: *`, and clears them for everyone else.
- **Errors:** `operations.MapError`: `409 duplicate_trip_id`, `409 duplicate_destination`, other unique keys `409 already_exists`, checks and foreign keys `422 invalid_argument`, the deferred tenant-consistency triggers `409 failed_precondition` (`tenant_mismatch`), RLS `403 permission_denied`; a row outside the reach is `404`.
- **Indexes (AC):** `explain_integration_test.go` loads a few thousand rows over three tenants, then plans every method of `operationsdb.Querier` (reflection keeps the list complete) plus 14 shapes of the sibling domains and definer helpers (payroll I1/I3, billing I20-I23 and the party axis, the standby axes, the evidence token, the dispatcher day list, the lookup inside `trip_seal_taken()`) under a request principal's RLS with `enable_seqscan` off: no operations table is read sequentially, each read uses an index its query names, and a negative control proves the check bites. `pgtest.Explainer` is the reusable `DBTX` that plans sqlc calls instead of running them. Every shape is served by the 0004 indexes (the all-customer billing axis through PostgreSQL 18's skip scan over `trip_records_party_axis`), so no index follow-up migration was needed.

Tests: `go test ./internal/operations/...` (the `tripDocId.test.ts` vectors and photo types in `tripcheck`, numbers, ranks, every malformed cursor on its own axis, reach, the standby projection, validation, error mapping) and `make test-integration` (`internal/operations/*_integration_test.go`: logitrack_app through `db.WithPrincipal`; the four acceptance criteria, concurrent numbering across tenants, kept canonical numbers moving the counter, concurrent queue positions that only the driver lock serialises, the duplicate-seal check across drivers, tenants and cancelled trips with concurrent submits, rename and history, merge by type, contractor reach one way, the helper's read, keyset pages on both task axes, the standby projection including a service fee that changes hands, stops, replays, the deferred tenant triggers, and the EXPLAIN check).

## Tenant stamping, task reassignment and the orphan scan (T28, issue #48; Appendix C §C.1.7, §C.3.10)

- **Stamping** (`operations.Stamp`): the tenant of a row the API writes into `tasks`, `trip_records`, `standby_records` or `incident_reports` is the chain of `tenancy.Resolve` (the port of `tenantResolve.ts`) over the links the writer can read, read with `tenancy.TenantOf` in its request transaction: tasks the driver's (`driver`), else the writer's active tenant (`form`, R13: a dispatcher's call-out lands in its organisation's tenant); trips the task's, else the driver's; standby the task's, the trip's, the driver's; incidents the trip's, the driver's. An unreadable or quarantined link is `422 <field> not_found`, an exhausted chain `422 tenant_orphan` (the API never quarantines), a tenant outside the writer's reach `403 permission_denied` `tenant_link_mismatch`. Every API path that creates one of these rows calls `Stamp` in its request transaction before `CreateTask` / `CreateTrip` / `CreateStandby` / `CreateIncident` and takes `tenant_id` / `tenant_source` only from its result: T31's `POST /v1/tasks`, `/v1/tasks/import`, `/v1/standby/backfill` and `/v1/incidents` (the dispatcher's call-out is proven end to end, `TestDispatcherCallOutLandsInItsTenant`); the driver app's `/v1/mobile/*` create routes of P7a (E7 #14) will. Write-back rows reach PostgreSQL through the mirror, which stamps them with the ETL mappers. The master data, assignments, installations, expenses and maintenance stamp `self` / `truck` / `driver` as before (T20-T23, T52S, T40).
- **R13 reassignment** (`PATCH /v1/tasks/{id}` with a `tenantId` other than the task's: `{tenantId, driverId?}`, `operations:manage_tasks` \| `platform:cross_tenant_write`): a dispatcher on a task it reads whose tenant is in its own write reach (its organisation's call-outs; another carrier's task it only reads through its parties' scope is `403 task_not_in_reach`, Appendix C §C.9.2 #12), or a platform admin. It is a move only: since T31 a body with the task's own `tenantId` (or none) is the ordinary update under the caller's RLS (a platform admin without `X-Act-On-Tenant` gets `403 act_on_tenant_required` instead of the mover's `422 tenantId same_tenant`); a move request that changes nothing answers `moved: false` and writes nothing. `iam.TaskMover` runs one system transaction after that authorization: the rules of Appendix B §B.2.11 (as built: open task, no trips, target active and not quarantine, the target's driver, helper and truck of the target or a contractor-linked tenant), `tenancy.MoveTask` (`app.tenant_move` for that move only; `tenant_source='form'`; standby records and files follow), the driver assignment under `LockDriverQueue` when the driver changes, `task_tenant_reassigned` in the same transaction (one row for the target tenant, one for the source) and outbox `task.reassigned` (driver changed) / `task.updated` (`changed: [tenantId]`, a kept driver). On the move path every other PATCH field is `422 not_supported` (move first, then update). `UPDATE … SET tenant_id` anywhere else fails in `t_freeze_tenant_id`.
- **Orphan scan** (`tenancy.orphan-scan`, daily 03:00 Bangkok): the worker's consumer runs `tenancy.Scan` read-only in a system transaction: quarantine rows per tenant-stamped table (from the catalog) and the R24 drift buckets `driverMoved` / `truckTenantMismatch` over the rows stamped `driver`; the job result carries both (lists cut at 1000, totals complete), the worker's `/metrics` the gauge `tenant_orphan_rows_total{table}`, and when the quarantine tenant holds rows `tenant_orphans_detected` (warning, platform-level) travels through outbox `security.event` to the `security.audit` consumer. Nothing is moved: the re-home is T24's quarantine routes and `etl quarantine resolve`.
- **security.audit**: `internal/security` `Audit` appends each outbox `security.event` once (`consumer_inbox`); a malformed body, an invalid event or an in-transaction type is acked as permanent. The first deployment drains what auth queued since T05 (`login_failed`, `login_lockout`, `password_reset_requested`).

Tests: `go test ./internal/operations/ ./internal/security/ ./internal/platform/tenancy/...` (the PATCH body, the authorization, the vocabularies, the consumer's refusals) and `make test-integration`: `internal/operations/stamp_integration_test.go` (every chain, the refusals, the dispatcher's call-out in its tenant with `form`, the `tenant_source` CHECK = `tenancy.Sources`), `internal/iam/tasks_integration_test.go` (Appendix C §C.9.2 #12, every refusal including another carrier's task and a driver change without a move, unassign, no-op, a kept driver as `task.updated`, the two event rows and the outbox rows, the route with its guard and body rules), `internal/platform/tenancy/tenancy_integration_test.go` (frozen tenant for staff and system, `MoveTask` with standby records and files, `TenantOf` under RLS, `Scan` over quarantine and both drift buckets with no row changed), `internal/platform/tenancy/orphanscan` (command -> job -> gauge -> `security.event` -> `security.audit` once) `cmd/seed` `TestOrphanScanReportsTheSeededBrokerDrift` (the smoke seed's `JB2` result) and `cmd/etl` `TestOrphanScanAfterTheFixtureLoad` (the fixture load against `orphan_scan.json`, with the broker driver's July task in `truckTenantMismatch`; `-update` rewrites it).

## Firebase bridge (T08, main spec §4.9, Appendix C §C.6)

`AUTH_FIREBASE_BRIDGE_MODE` decides what the web and the APK may do with Firebase credentials while the strangler runs; no Firebase Admin SDK is linked (`internal/auth/firebase`). Nothing reaches Google at start-up: keys and OAuth2 tokens are fetched on first use.

| Mode | Custom tokens for the web | APK Firebase ID tokens | Account mirror | Phases |
|---|---|---|---|---|
| `off` | no (`/v1/bridge/*` 404) | no (404) | no | local default; after P8 |
| `web` | yes | no | yes | P0-P6, until TW7 |
| `mobile` | no | yes | yes | P7a-P8 |
| `both` | yes | yes | yes | only while P7a overlaps an unfinished TW7 |

- **Web** (`POST /v1/bridge/firebase-token`, internal listener only, bearer): an RS256 custom token signed with the `GOOGLE_APPLICATION_CREDENTIALS` service account for the caller's Firebase uid (`users.legacy_auth_uid`; an own-fleet user created in Go gets `users.id` at the first mint) with the legacy claims of its active context (`admin`, `role`, `driverId`, `customerScopeId`, `partnerScopeId`, Appendix C §C.6.3). Only own-fleet staff, `platform_admin` and users imported from a legacy partner or customer claim (an `auth_identities` `firebase_legacy` row) get one; everyone else `403 permission_denied`. `GET /v1/me` adds `legacyAuthUid` in this mode.
- **Firebase ID tokens** (`auth.Service.VerifyFirebaseIDToken`): go-oidc against `https://securetoken.google.com/{FIREBASE_PROJECT_ID}` with the securetoken JWKS; the principal (`amr` `firebase`, no session) comes from PostgreSQL, never from the token's claims. `FirebaseAPK` (the exchange of T55) needs a mode with `mobile`; `FirebaseShim` (T32) works in every mode. A Firebase token is never a bearer: `401 invalid_token` on every route.
- **Account mirror** (every mode but `off`): password sets (change, reset, ticket change, temporary password), disable / enable, a soft delete (every session revoked with reason `disabled`: the account is disabled), an admin revocation of every session and claims changes are written to Firebase Auth through Identity Toolkit inside the request's transaction, before COMMIT; a failure is `503 bridge_unavailable` and commits nothing in PostgreSQL. A creation that fails after Firebase created the account deletes it again, and a retry adopts an orphan that survived (a uuid uid nobody in PostgreSQL holds); an email held by any other Firebase account is `409 already_exists` (`details.reason` `firebase_account_exists`). The service account needs Firebase Authentication Admin on `FIREBASE_PROJECT_ID`; a 401 / 403 from Identity Toolkit is logged at error level as that misconfiguration. Entry points used by T19's `internal/iam` administration: `RevokeInTx`, `SetStatusInTx`, `NewTemporaryPassword` + `SetTemporaryPasswordInTx`, `MirrorNewUserInTx`, and `MirrorEmailInTx` (T19: an email change, `firebase.Update.Email`). Metrics `auth_firebase_mirror_failures_total{op}`, `auth_firebase_custom_tokens_total`.

Tests use `internal/auth/firebase/firebasetest` (securetoken keys, OAuth2 token endpoint and Identity Toolkit in-process); nothing reaches Google. Signing a minted token in to the dev project is an owner step (Appendix C §C.9.5).

## Web flags (T17, main spec §10.6, §12.1)

`GET /v1/config/web-flags` (internal listener only, unauthenticated, `Cache-Control: no-store`) answers `{"data":{"domains":{"auth":"go","masterdata":"firebase",...}}}` for the nine domains `auth, masterdata, operations, billing, hr, comms, security, mobile_release, dashboard`. A domain listed in `PG_OWNED_DOMAINS` (empty, `all`, or a comma list) is `go`; each `WEB_FLAG_OVERRIDES` entry `domain=go|firebase` then replaces its domain, e.g. `auth=go` in P0 or `billing=firebase` to roll the billing pages back. Both are parsed at start-up and a bad value stops the api (exit 2, the message names the variable, never its value). The web reads the endpoint through the BFF as TanStack `['webFlags']` and polls it every 60 s, so a rollback is an edit of `WEB_FLAG_OVERRIDES` in `.env` plus `make api-reload`, with no web rebuild (R35, R41). The target runs `docker compose -f deploy/docker-compose.yml --env-file .env up -d --no-deps --wait api` from `logitrack-api/`, which recreates only the api with the new value and waits for it to be healthy; a bare `docker compose up -d api` finds no compose file here and, run from `deploy/`, reads no `.env`, and `docker compose restart` keeps the old environment. `make up` also works but rebuilds and waits on the whole stack. The Redis key `cache:web_flags` stays unused: the value is the api's own env.

## Coexistence: etl.sync mirror and firestore.shadow projection (T24S, issue #44; main spec §12.1, §13.7-§13.8, R25, R71)

From the P1 load until P7b every Firestore field has one writer. `PG_OWNED_DOMAINS` decides which (`internal/etl/coexist.go`):

| Collection | Domains not all PostgreSQL-owned | Domains PostgreSQL-owned |
|---|---|---|
| every mapped class A or B collection | **mirrored whole** (FS->PG through the load transforms) | not mirrored; projected when it is in the projection list |
| the class C collections: `tasks`, `trip_records`, `standby_records`, `incidentReport`, `vehicle_expenses`, `maintenance`, `chats`, `messages`, `leave_requests`, `mobile_installations` | **mirrored whole** | **mirrored whole**: the installed 3.x APKs write them in Firestore until P7b whatever the domain flag says (billing at P3, hr at P4, comms at P5); P7b stops them by switching `ETL_SYNC_ENABLED` off |
| `users` (loaded by `auth-import` at P0; `permissions_config` is `auth-rbac`'s and never mirrored) | not mirrored (before P0) | **field mirror** of the 3.x app's class C fields: a sign-in (`lastLogin` + `lastLoginLat/Lng/GeoSource/LocationAccuracyM`) -> `users.last_login_*` when newer than PostgreSQL's; `fcmTokens` -> the user's `device_tokens` rows of `legacy_source users.fcmTokens`, replaced as a set; an unknown uid is rejected `user_unresolved` |
| `drivers` | whole | **field mirror**: `activeTruck` -> `active_truck_id`, `active_truck_plate`, `active_task_id`, `active_started_at` (cleared when the app deletes the map) and `fcmToken` -> the driver's legacy `device_tokens` row (`legacy_source drivers.fcmToken`; replaced or deleted with the app's token; stored only when the document's `authId` is the linked login's Firebase uid; rows a device registered itself are never touched); `currentTruckId` stays in `etl.source_docs`; a document with no driver row is rejected (`driver_unresolved`) |
| `hubs` | whole | **field mirror**: only the hubs drivers create (`createdByDriver`): inserted, then kept Firestore's (the projection skips them); a driver hub whose code PostgreSQL already holds -> rejected `duplicate_hub_source_id`, mapped to that hub; any other new hubs document -> rejected `hub_unresolved` |
| `trucks` | whole | **field mirror while billing is Firestore-owned**: the maintenance flow's `truckStatus`, `currentMileage`, `lastServiceDate`, `nextServiceMileage`, `lastAlertMileage`, `activeMaintenanceId` (`checkMaintenanceAlert`, the web maintenance pages); the projection leaves those six out of an existing document until billing is owned (a document it creates gets them from PostgreSQL), so a truck-form edit of one of them in Go stays in PostgreSQL until the maintenance flow writes it again (the reconciliation reports the difference); a truck whose fields the mirror changed gets `truck.updated`, so its projected `updatedAt` follows the row |

A field mirror applies a field only when Firestore changed it since the document was last recorded (the P1 load or the previous sweep), so a projected write, which moves the document's update time, never brings a stale value back over a PostgreSQL edit; of a document never recorded (one the projection created) or never applied (a users document the load recorded `pending`) only the fields it holds, so an absent field never clears PostgreSQL's value. It replaces only the findings of the fields it applied, so the P1 load's findings on the other fields of a document stay open; a document rejected because its row did not exist yet is applied again once the row exists, its stale finding resolved `fixed_at_source`.

- **`etl.sync` (worker, group sync)**: a `job.etl.sync` command (the scheduler's cron every `ETL_SYNC_INTERVAL` while `ETL_SYNC_ENABLED`; whole minutes that divide an hour, `*/5` by default) runs one sweep (`etl.Engine.Mirror`): each planned collection is read as one consistent snapshot (`gcp.Firestore.Documents`), then applied in one transaction under the load lock, documents before the watermark minus 10 minutes skipped, a document applied only when its `_updateTime` is newer than `etl.source_docs`; watermarks advance like a load's. The sweep is the ETL load path, so it uses its own pool on `ETL_DATABASE_URL` (`logitrack_etl`, R66; any other login fails the job; a failed login check goes to the retry ladder) and `db.WithETL` (`app.etl_load`, allowed only here and in `cmd/etl` by `tools/analyzers/withsystem`); its `jobs` row is written on `DATABASE_URL`. That URL bypasses RLS, so only the replica that runs the mirror holds it: `worker-sync` (compose profile `coexist`), the worker with `WORKER_CONSUMERS=sync` alone and `ETL_SYNC_ENABLED=true`; any other worker refuses to start holding the URL, and with the mirror on the other replicas leave group `sync` out (`WORKER_CONSUMERS=billing,notify,documents,integrations,hr,platform`). One document never stops a sweep: each applies in a savepoint; an out-of-vocabulary literal keeps PostgreSQL's value of its field (`status_out_of_vocab` with the literal; the rest of the document applies); a billable document that still cannot be applied (R19) is held (recorded `pending` with its finding, retried by every sweep, `mirror_apply_total{result="held"}`, named in the job result and reported by `reconcile-sync`) while the rest of the sweep commits. A database without the P1 load fails the job (acked; the next fire tries again); a Firestore or database outage goes through the retry ladder. With `ETL_SYNC_ENABLED=false` a command fails its job (`the FS->PG mirror is off on this worker`). `mirror_apply_total{collection,result}`. The sweep reads whole collections (every collection of one sweep at the read time of its first read since T29) and stays the catch-up behind the listeners below.
- **Operations mirror hardening (T29, issue #49; main spec §13.7 as built T29)**:
  - **Listeners**: on `worker-sync`, beside the consumer, one loop polls `tasks`, `trip_records`, `standby_records` and `incidentReport` every `ETL_LISTEN_INTERVAL` (default `2s`; `0` = off) while it holds the lease `lock:mirror:listen` (TTL `max(30 s, 3 × ETL_LISTEN_INTERVAL)`, renewed every tick and every third of the TTL while a poll runs, so a long poll keeps it; a poll whose renewal fails is cancelled and its cursors restart from the watermarks; a second replica waits). The Firestore REST API has no streaming listen, so a poll is a `runQuery` per collection on `updatedAt >= cursor - 1 min` ordered by `updatedAt` and name (`gcp.Firestore.Changed`, the default single-field index), every collection at one read time, applied in one transaction through the same transforms (`etl.Engine.MirrorChanges`). A listener never moves `etl.watermarks` and never removes rows; a document it cannot decide alone (a rejection or a hold needs the whole collection) is left to the sweep (`mirror_apply_total{result="deferred"}`). A write without a timestamp `updatedAt` waits for the sweep. `updatedAt` is the writer's clock, not the commit time (the 3.x app writes `DateTime.now()` on all four collections: `delivery_trip_repository.dart`, `checkin_repository.dart`, `standby_repository.dart`, `incident_report_repository.dart`): a clock behind by up to the 1 min overlap is still seen, one behind by more waits for the sweep, and one ahead never moves a cursor past the poll's read time (the cursor is the newest `updatedAt` read, capped at the read time), so one phone dated ahead cannot hide the correctly-clocked writes behind it. Cursors start at each collection's watermark minus the overlap, so a restart after a gap loses nothing (and the sweep applies everything anyway).
  - **Domain events** (`internal/etl/mirror_events.go`): each applied document of the four collections is compared with its row before and after, and what changed is appended to the outbox in the mirror's transaction: `task.created|assigned|reassigned|cancelled|checked_in|updated` (+ `task.plan_date_changed`), `trip.created|delivered|cancelled|resubmitted|updated` (+ `trip.delivered_at_changed` for a delivered trip whose delivery time moved), `standby.completed`, `standby.customer_assigned`, `incident.created`; thin payloads (`entity`, `id`, `changed[]`, `source: mirror` + the fields of Appendix B §B.4.3), the tenant and dispatch topics, the drivers' queues for task events. A version that changes nothing PostgreSQL holds (a Cloud Function's billing fields, an unmapped field) and a row in the quarantine tenant emit nothing; one delivering update is exactly one `trip.delivered`. Since T33 a payload also carries `at` (the document's Firestore update time) and the dispatch topics are those of the parties the row involves after the version and, for an update of the same row, before it (a party change reaches the board that loses the row; the parties it left are named in `leftPartyIds` and get the envelope only; a claim of another driver's trip or a Q3 copy is its own row and reaches only its own parties); the relay keeps only the thin keys on the realtime topics ("Realtime"). Every event carries the header `origin=etl.sync`: `notify.fcm` acks it without a push (the Firestore-side writer notified already; T31's write-back handlers emit their own notify events), while SSE, `firestore.shadow` and `billing.compute` take it as any event. `mirror_events_total{collection}`.
  - **Renames**: renameTripRecord's batch (copy to the new id with `renamedFromTripId`, re-point the incident reports, delete) is applied as an update of the trip's row: `legacy_doc_id` and `trip_no` take the new id, one `trip_no_history` row, the old document's `etl.source_docs` entry becomes a `renamed` tombstone at the batch's commit (migration `0018`; its findings resolved `fixed_at_source`), one `trip.updated` with `previousTripNo`. The tombstone is what keeps an overlapping run (a sweep that read before the rename and commits after a listener applied it, or the other way round) from loading its copy of the old document as a second row with a second `trip.delivered`: the copy is not newer, so the update-time guard skips it. Only the trip's own driver can rename it: a document whose `renamedFromTripId` names another driver's trip loads as its own row with a `trip_no_mismatch` finding and no history (`firestore.rules` let any driver create a trip document). A copy whose original still exists (rename-trip-doc.js, Q3) stays its own row; a trip renamed twice between two reads loads as a new row and its first id is reported.
  - **Removed** (a sweep's document Firestore no longer has): removed only where the legacy app deletes (`billing_statements` drafts, `customer_service_fees`, `holidays`, chat `messages`, `broadcasts`, `waitlist`; a sent or paid statement, a voided broadcast (its document was the projection's to delete, T48), a row still referenced, and every other collection are kept and reported `deleted_at_source` / `ops_rows_without_document`); `standby_rate_entries` stay (a void needs the staff member, R20). A collection read empty removes nothing. A sweep judges only what its snapshot can see (an entry recorded at a version newer than the sweep's read time was created after it), and a removed document's entry becomes a `removed` tombstone at the sweep's read time, so a sweep that read before a create or a delete and commits after a newer one (a hand-run `etl mirror` beside the worker's) neither removes the new row nor brings the removed one back. `mirror_apply_total{result="removed"}`.
  - **Read-your-writes** (R53): after each sweep or poll commits, `cache:mirror_ack:{collection}:{doc_id}` is raised to the applied update time of every loaded or quarantined document (`cache.Cache.SetMirrorAck`); a write-back handler waits for its own write's update time with `WaitMirrorAck` (3 s, else `202`; the operations write routes of T31 do, `internal/coexist/writeback_integration_test.go` runs the round trip). Only the four operations collections have a listener: every other mirrored collection (`vehicle_expenses`, `maintenance`, `chats`, `messages`, `leave_requests`, `mobile_installations`, the class A and B collections) is acked by the sweep alone, so a write-back on one of them answers `202` unless its task adds a listener (`etl.ListenFields`; noted on T40 #60, T45 #65, T47 #67). T45 adds none: a leave decision written back answers `202` after the wait until the next sweep (`ETL_SYNC_INTERVAL`) has applied it.
  - **Lag**: `mirror_lag_seconds{collection,path}` = commit of the apply minus the document's Firestore update time, `path` the run that applied it (`listener` or `sweep`). The SLO p95 < 5 s holds for `path="listener"`, the four operations collections; `path="sweep"` is the catch-up of everything else (up to `ETL_SYNC_INTERVAL` plus the sweep's own length) and has no SLO. Alert rule for the operator's Prometheus: `histogram_quantile(0.95, sum by (le, collection) (rate(mirror_lag_seconds_bucket{path="listener"}[5m]))) > 30` for 5m. Measuring it per listened collection against a dev Firestore project is a hitl step.
  - **Operations reconciliation**: per document of the four collections the columns the boards, the monitor and billing read (task status, type, plan instant, number; trip status, number, delivery time; standby start and end; incident cause, text and its trip, a former number included) equal what the transforms read from the document (`ops_fields`; a field with an open finding is skipped), and rows whose document is gone are listed (`ops_rows_without_document`, informational). The listeners keep applying while it runs, so a document is compared only with the row of its own version: one statement reads the recorded version, the open findings and the columns together, and a row a listener moved past the snapshot is skipped (counted "moved on since the read" in the note), never reported as a difference.
- **`firestore.shadow` (worker, group sync, prefetch 4)**: projects `hubs.changed` (the hubs and their distance pairs), `customers.changed`, `companies.changed`, `truck.*`, `driver.*`, `assignment.*` (the assignment, the truck's `currentAssignments[]`, the driver's `currentAssignment`), `tenant.*` (the carrier profile `subcontractors/{id}`), `settings.changed` of `distances_last_calculated` (every pair and `metadata/distances_last_calculated`) and of `mobile_app` (the version gate `settings/mobile_app`, T52R, once `mobile_release` is PostgreSQL-owned; a gate document of another flavor is held, see "Mobile installations and releases" above); `holidays.changed` (T45, once `hr` is PostgreSQL-owned: the public calendar and the own fleet's holidays as `holidays/{id}` in the legacy shape, `date` the UTC midnight of the day as the legacy callables stored it, `type` and `status` upper case; a carrier's own holidays are skipped, since Firestore holds one calendar; the documents of deleted holidays, named by the event's `deletedDocIds`, are deleted, and so is the minted document of a row that vanished while it was projected, so a create racing a delete leaves nothing behind; `projection_writes_total{result="deleted"}`); `trip.priced`, `trip.repriced` and `standby.priced` (T38, once `billing` is PostgreSQL-owned: the price fields of the trip and standby documents, see "Compute-on-delivery and backfills"); `broadcast.created`, `broadcast.voided` and `broadcast.read` (T48, once `comms` is PostgreSQL-owned: `broadcasts/{id}` of the platform-wide broadcasts and the own fleet's group sends in the legacy shape, a carrier's and a send to selected users skipped; a voided broadcast's document is deleted while its row stays, `projection_writes_total{result="deleted"}`, and deleted again by a send's projection that wrote it while the void committed; `readDriverAuthIds` and `readCount` merged with PostgreSQL's readers, never removing one); the other settings keys project nothing. As `logitrack_app` in `db.WithSystem` it re-reads the rows and writes, per document, only the masked fields whose stored value differs (an equivalent legacy spelling such as `spx` for `SPX`, `RETURN_CENTER` for SOC, a `yyyy-MM-dd` date or a download URL with its token is kept; an unchanged document is not written at all, so the mirror sees no change from it), under a precondition on the update time it compared with; the one-document `settings/mobile_app` and `metadata/distances_last_calculated` are projected one projection at a time (a transaction advisory lock over the encode, the read and the write), so of two quick changes the later one always ends in Firestore. Ids (R25): `legacy_doc_id`, else `id::text` minted into `legacy_doc_id` in a transaction of its own that commits before anything reaches Firestore (a sweep that reads the document finds its row), the document carrying the `updated_at` the minting `UPDATE` leaves; a distance pair is projected under its natural id `{hub}_{soc}` / `{soc}_{hub}` because the 3.x app reads pairs by it (the hub code spelled as its loaded pairs spell it; minted again under the new code after a hub code change, the former document losing its distance and duration); a path that is not a valid document id (a `/` in a code) is skipped, never stopping the pass. `authId` follows the linked login's Firebase uid (removed after an unlink; a P1 uid no login holds stays), so every write that moves a driver's login emits `driver.updated` (user creation with a driver, driver-link put and delete, user delete, the bridge giving a linked login its uid), and a re-home emits the events of the drivers, trucks and companies it moved. `customers.changed` also projects the hubs linked to the customer (`linkedCustomerName` = `CODE — Name`) and the drivers holding its codes (`customerDriverIds`, merged per entry under the stored key; an unresolved entry stays), `tenant.updated` the hubs linked to the carrier. ## Web BFF and edge gate (TW3, main spec §10.3-§10.5, Appendix E §E.8)

The browser never calls Go: `logitrack-web` serves `/api/go/v1/*` (generic proxy: the HttpOnly `lt_at` cookie becomes the bearer, `PUT /v1/uploads/local/*` keeps the browser's `Content-Length` and gets 5 min instead of `GO_API_INTERNAL_TIMEOUT_MS`, the session routes `v1/auth/(login|google|refresh|tenant|logout|logout-all|sse-ticket|exchange)` and `v1/bridge/*` are 404, mutations need a same-origin `Origin`), `/api/auth/*` (the only routes that call the token-bearing auth routes and set `lt_at` `Path=/` / `lt_rt` `Path=/api/auth`) and `proxy.ts` on `/app/*` (verifies `lt_at` against this api's JWKS, then reads the capabilities from `GET /v1/me`, cached per `(sid, ver, tid)` for 60 s). ## Billing engine (T36, main spec §6)

`internal/billing/compute` prices trips and standby events with no I/O and no clock: the caller loads rate cards, fuel rounds, fees, hub names and period locks in its pricing transaction and passes them in. Money stays float64 and matches V8 bit for bit: `jsmath.Round` rounds ties toward +Inf (and keeps `-0`), every product is wrapped in `float64(...)` so arm64 and amd64 `GOAMD64=v3` cannot fuse it into a multiply-add, and sums stay unrounded in input order. Deliberate differences from the TypeScript: a blank vehicle class is `no_vehicle_class` (R15), equal effective instants are ordered by legacy doc id, `created_at`, `id` whatever the load order (R16), a trip with no plan, delivery or creation instant is `no_billing_date` instead of `Date.now()` (R19), voided standby rates never price (R20). `IsFrozen` / `CarriesFuel` exist once in the module.

## Async processing (T10, main spec §7, Appendix B §B.5)

- **Emit**: `outbox.Append(ctx, tx, outbox.Event{...})` in the service transaction is the only way to publish (auth's events included; it validates the routing key and topics and carries `requestId` and `traceparent`); `api` never connects to RabbitMQ. Admin jobs: `jobs.Service.Submit` (lock + row + `lt.jobs` command in one system tx after Go authorization, `202 {jobId}`).
- **Relay** (scheduler leader, `pg_try_advisory_lock(hashtext('lt-scheduler'))`): `LISTEN outbox_new` + `OUTBOX_RELAY_INTERVAL`, `OUTBOX_BATCH_SIZE` rows `FOR UPDATE SKIP LOCKED`; per row its hook, then `Cache.OnEvent` (drops the `cache:` keys the event makes stale and announces them on `rt:cache`; nothing for events outside `cache.InvalidatingEvents`), publisher confirms, then one Lua script per realtime event (`INCR rtlog:seq`, `XADD rtlog:{topic} {seq}-0`, `PUBLISH rt:{topic}`), then `published_at`. A failed hook, cache invalidation, publish or realtime step stops the batch at that row (`attempts`, `last_error`); a row whose publish was confirmed before a later step failed is not published again; rounds back off from the interval to 30 s while the head row keeps failing. The scheduler's Redis client and keyspace come from `cache.Open`, like the api's: every key (`rtlog:*`, `rt:*`, `lock:job:*`, `lock:cron:*`) is built by `cache.Keyspace`. Hook: `user.sessions_revoked` re-applies auth's revoked markers and cached version (`auth.RevocationHook`, `JWT_ACCESS_TTL`). Metrics `outbox_pending`, `outbox_lag_seconds`.
- **Consume** (worker): the topology is asserted at every connect; each queue of the `WORKER_CONSUMERS` groups that has a consumer runs with its Appendix B prefetch. A handler returns `nil` (ack), `mq.Permanent(err)` (ack, outcome recorded) or any other error: retry through `lt.retry` (`10s`, `1m`, `5m`, `30m`, `2h`), back to that queue only via `lt.requeue`, and the sixth failure goes to `{queue}.dead`. DB side effects run through `inbox.Run` (claim in `consumer_inbox` first, `db.WithSystem` with the event's tenant). Metrics `mq_messages_total{queue,outcome}`, `mq_dead_letter_depth{queue}`.
- **Consumers today**: `cartrack.sync` (T53, see "Vehicle locations, dashboard and forms"), `security.audit` (T28: the consumer-written `security_events` rows of outbox `security.event`, once per message through `consumer_inbox`), `tenancy.orphan-scan` (T28, see "Tenant stamping, task reassignment and the orphan scan"), `notify.email` (reset and invite links, Mailpit locally; `user.created` mails an invite only with `sendInvite: true`), `distances.compute` (T21, see "Hubs and distances"), `billing.compute` and `billing.backfill` (T38, see "Compute-on-delivery and backfills") and `notify.fcm` (T13: task pushes in the legacy format, silent `tasks_changed` once per driver per 30 s, `session_revoked` to the device of a revoked session, T47: `chat` to the driver of a staff chat message; `idem:fcm` claims make every push at most once per token: a send whose answer was lost after the request reached FCM is logged `failed` "outcome unknown" and never resent; at most 10 devices per driver; off with `FCM_ENABLED=false`). The other queues fill with their issues; the worker logs which queues have no consumer yet.
- **Readiness** (`/readyz` on `METRICS_ADDR`): worker = PostgreSQL + Redis + its RabbitMQ session; scheduler = PostgreSQL + Redis, plus the broker connection while it is the leader. A failure is `503 unavailable` with `details.checks`.
- **Cron** (Bangkok, leader only, `lock:cron:{job}:{scheduledFor}`): `auth.token-cleanup` every 10 min, the commands `storage.gc` hourly and `tenancy.orphan-scan` at 03:00 (T28) and `billing.safety-net` every 15 min (T38), and at 04:00 `outbox.prune`, `inbox.prune`, `jobs.prune`, `idempotency.prune`, `rtlog.trim`; the command crons of §7.4 join with their consumers (`scheduler.Pending`); `bangchak.snapshot` (T37) is `scheduler.Gated` behind `FUEL_MONTHLY_SNAPSHOT_ENABLED`, `etl.sync` (T24S) behind `ETL_SYNC_ENABLED` and `cartrack.sync` (T53, every three minutes) behind `CARTRACK_SYNC_ENABLED`.
- **Jobs API**: `GET /v1/jobs`, `GET /v1/jobs/{id}` (owner, a platform role, or staff of the job's tenant holding its type's capability in `jobs.TypeCapabilities`: `distances.compute` -> `operations:calculate_distances` since T21) and `POST /v1/admin/queues/{queue}/replay` (platform_admin) are mounted by `cmd/api` behind `auth.RequireAuth` (`app.JobGroups`). A replay creates a `queue.replay` job; the leader moves `{queue}.dead` back to `{queue}` with a fresh retry budget.
- **Tests**: `make test-integration` runs `internal/platform/{mq,outbox,inbox}`, `internal/jobs`, `internal/scheduler` and `internal/notify` against postgres:18-alpine, rabbitmq:4-management-alpine, redis:7-alpine and axllent/mailpit (images read from the compose file).

## Object storage (T11, main spec §9, §9.11)

`internal/storage` keeps the `file_objects` registry (R1) behind one `Backend` interface with two implementations; `STORAGE_BACKEND` picks the backend of **new** uploads and every row records its own (`file_objects.storage_backend`, migration 0011), so reads, commits, re-signs and `storage.gc` follow the row.

| Env | Processes | Default | Notes |
|---|---|---|---|
| `STORAGE_BACKEND` | api, worker, seed | `s3` | `local` or `s3`; compose keeps `s3` |
| `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_USE_PATH_STYLE`, `S3_USE_SSL` | api, worker | -, -, -, -, `true`, `false` | required with `s3`; an endpoint scheme must agree with `S3_USE_SSL` |
| `S3_BUCKET`, `S3_PUBLIC_BUCKET` | api, worker | `logitrack`, `logitrack-public` | also label local rows |
| `S3_PRESIGN_ENDPOINT`, `S3_PUBLIC_BASE_URL`, `CORS_ALLOWED_ORIGINS` | api | - | the origin URLs are signed for (required with `S3_ENDPOINT`), public-bucket base, browser origins |
| `S3_PRESIGN_GET_TTL`, `S3_PRESIGN_PUT_TTL`, `UPLOAD_MAX_BYTES` | api | `1h`, `15m`, `10485760` | also bound local URLs and uploads (max 100 MiB; an APK on the internal `/v1/uploads/local/` route up to `storage.MaxReleaseBytes`, 200 MiB, held in memory) |
| `LOCAL_MEDIA_DIR` | api, worker, seed | - | absolute; required with `local`; keep it set after a switch to `s3` while local objects exist |
| `LOCAL_MEDIA_PUBLIC_BASE_URL`, `LOCAL_MEDIA_SIGNING_KEY` | api | - | required with `LOCAL_MEDIA_DIR`; the key (secret, >= 32 bytes) signs local URLs |
| `EVIDENCE_TOKEN_TTL_DAYS`, `EVIDENCE_PRESIGN_TTL` | api | `0`, `15m` | `0` = evidence tokens never expire (R30); with a TTL a token's age counts from its embedded issue time (legacy tokens: the row's `created_at`) |

- **Presign** `POST /v1/uploads/presign` (internal, bearer, `presign_user` 120/min): purpose allow-list (`storage.Purposes`, key templates of main spec §9.2), content types, `sizeBytes <= UPLOAD_MAX_BYTES`, `pending` row (24 h), signed PUT bound to the declared type and size (`Content-Type` and `Content-Length` signed on both backends: the client sends a body of exactly `sizeBytes`, never chunked). `s3`: URL on `S3_PRESIGN_ENDPOINT` (never `S3_ENDPOINT`), signed offline, with `If-None-Match: *` signed too, so the URL only creates the object (a second PUT, also after the commit, is 412: after a lost response the client just commits). `local`: `url` is the API path `/v1/uploads/local/{key}?X-LT-Expires&X-LT-Signature` (web through the BFF: `/api/go` + url); the driver app gets `${LOCAL_MEDIA_PUBLIC_BASE_URL}/{key}?...` (`PUT /media/{key}`, public listener). `key` re-signs a pending upload of the caller.
- **Commit** `storage.Service.Commit(ctx, tx, CommitInput)` in the entity transaction: lock the row, Stat on its backend, size / type / sha256 as declared, `committed` + owner + outbox `storage.object_committed`; any failure is `422 invalid_argument` naming the key and the row stays pending. First caller: `PATCH /v1/me {photoKey}` (`user_photo`); `GET /v1/me` signs `photoUrl`.
- **Download** `GET /v1/files?key=` (internal, bearer) 302 to a short-lived URL on the row's backend. Readable are public objects, own uploads and everything under `X-Act-On-Tenant: *`; then a registered `storage.Authorizer` of the file's owner kind decides (authoritative: it narrows as well as widens); without one, staff of the file's tenant or of its contractor (`p_read`), narrowed per purpose (`Purpose.ReadCapability` / `NoStaffRead`): driver ID cards and licences need `drivers:view_pii`, leave evidence `hr:view_leave`, penalty evidence `hr:view_payroll`, statement documents `accounting:billing_result`; reports and tenant ID cards have no staff rule. URLs live `S3_PRESIGN_GET_TTL` capped per purpose (`Purpose.GetTTL`: 5 min PII, 15 min documents and HR files), entity payloads (`SignedURL`) included.
- **Local backend**: files under `LOCAL_MEDIA_DIR/{private,public}/{key}` (0640, dirs 0750) with a `.meta/` sidecar (type, size, sha256), atomic writes through `.tmp/` (temp + fsync + rename), all access through `os.Root` (no traversal, no symlink escape). `GET|HEAD /media/{key}` (public listener) needs a valid signature except under `app_releases/`; a path ending in `/` is 404; tampered or expired signatures 403. Upload URLs sign method, key, expiry, `Content-Type` and `Content-Length`. A request head that carries a valid signature gets the signed size as its body limit (at most `UPLOAD_MAX_BYTES`; an APK on the internal route up to `storage.MaxReleaseBytes`, 200 MiB) and a 5 min read timeout (`ingress.Group.Uploads` -> `Service.UploadLimit` in fasthttp `HeaderReceived`, before the body is read); any other request, an unsigned PUT on these routes included, keeps the 4 MiB / 30 s defaults. The handler stages the bytes under `.tmp/` and renames them into place only under the lock of the pending local row (`PublishLocal`, the lock `Commit` takes), so a still-valid URL can neither overwrite a committed object nor swap bytes during a commit (409 `not_pending`). Key segments are limited to 255 bytes (250 for the last, its sidecar adds `.json`); the shared `ValidateKey` has no segment limit, so long legacy keys stay readable on s3.
- **S3 bootstrap**: the api re-asserts both buckets, the `app_releases/`-only public policy, the private bucket's CORS and the 30-day `cache/` lifecycle in the background until it succeeds. It owns only the anonymous grants (the public bucket's `LogiTrackPublicAppReleases` statement; none on the private bucket) and the `expire-cache` rule: other policy statements (deny rules, named principals) and lifecycle rules are read back and kept, and nothing is written when the bucket already matches; the private bucket's CORS belongs to `CORS_ALLOWED_ORIGINS`. The pinned MinIO answers `NotImplemented` to bucket CORS, so compose's server-level `MINIO_API_CORS_ALLOW_ORIGIN` (from `CORS_ALLOWED_ORIGINS`) is the CORS in force. `/readyz` checks the active backend.
- **storage.gc**: hourly command cron (scheduler) -> worker queue `storage.gc`: expired pending rows deleted with their objects on their own backend, one row per transaction; committed and `missing_at_source` rows never; partial local uploads older than 1 h swept.
- **Evidence** (R30, R47): `storage.NewEvidenceToken` (v1: version byte, 8-byte Unix issue seconds, 16 random bytes, base64url, 34 characters; the issue time is readable from the link; legacy 16-character tokens load unchanged), `Service.ResolveEvidence` (trip first, then standby; revoked or, with a TTL, expired -> not found), `RevokeEvidence`, `EvidenceTokenForSend` (a revoked token is replaced only by a forced send), `EvidenceImageURL` (`EVIDENCE_PRESIGN_TTL`). The gallery route itself lands with P5.
- **Deployment with nginx (first VM)**: `STORAGE_BACKEND=local`, `LOCAL_MEDIA_DIR` outside any web root, `LOCAL_MEDIA_PUBLIC_BASE_URL=https://logi.showkhun.co/media`, nginx `location /media/ { proxy_pass http://127.0.0.1:<API_PUBLIC_ADDR port>; client_max_body_size <UPLOAD_MAX_BYTES>; proxy_request_buffering on; }` (path unchanged; request buffering is nginx's default and must stay on, so a slow uplink or a head-only request is absorbed by nginx), and the BFF forwarding `PUT /api/go/v1/uploads/local/*` bodies up to `UPLOAD_MAX_BYTES` with their `Content-Length` and a 5-minute timeout instead of `GO_API_INTERNAL_TIMEOUT_MS` (Appendix E §E.8.2). Migrations: `migrate up-to 9` then `migrate apply 11` (0011 is the storage column; 0010 waits for the P1 sign-off).

Tests: `go test ./internal/storage/...` (keys, local backend, signatures, media routes, URLs signed for the presign origin) and `make test-integration` (`internal/storage`: compose MinIO + PostgreSQL: browser CORS preflight and PUT from `http://localhost:3000`, sized and create-once S3 PUTs (403 on another length, 412 on a second PUT), 422 commits, presigned GET expiry (skew-tolerant poll), driver PII reads, GC on both backends, the backend switch, the production P0 schema (`up-to 9` + `apply 11`), a local PUT racing a commit, bootstrap keeping operator bucket settings, evidence verifier; `internal/app`: the local flow end to end through both listeners, unsigned heads refused with 413).

## Realtime (T12, main spec §8, Appendix B §B.4)

| Route | Listener | Credential | Implicit topics |
|---|---|---|---|
| `GET /v1/events[?topics=&lastEventId=]` | internal (404 on public) | bearer (the BFF forwards `lt_at`); a `ticket` parameter is `400` and is not spent; `lastEventId` is read only without a `Last-Event-ID` header | `sse.WebTopics`: `user:{uid}`, `driver:{did}`, `global` (staff), `platform:security` (platform principals with `security:view_audit`), `dispatch:{partyId}:tasks\|trips` per party of a dispatcher's grant (instead of tenant tasks/trips), `tenant:{tid}:{family}` by capability (+ the same families of contractor sub-tenants for own-fleet staff), `tenant:{tid}:config` (members) |
| `GET /v1/mobile/events?ticket=[&topics=]` | public (and internal), 404 unless `MOBILE_SSE_ENABLED` | single-use ticket from `POST /v1/auth/sse-ticket` (60 s, `GETDEL`); never a bearer | `user:{uid}`, `driver:{did}` |

- **Fan-out**: the scheduler's relay writes (`realtime.Writer`: `INCR rtlog:seq`, `XADD rtlog:{topic} {seq}-0`, `rtlog:marks`, `PUBLISH rt:{topic}`); every api replica runs one `realtime.Hub` (`PSUBSCRIBE lt:{env}:rt:*`, started by `API.OnServe`) that hands each message to the local streams of its topic without blocking (a full 1024-message buffer ends that stream with `reconnect` `lagging`; a re-established subscription ends every stream with `reconnect` `interrupted`, since Redis keeps nothing for a disconnected subscriber).
- **Per-topic payloads (T33, issue #53)**: the writer gives each topic of an event the payload `realtime.Project` allows it (one script, one sequence number; a topic without a copy gets no entry and no message; an event no topic carries takes no number). The task, trip, standby and incident events keep only the thin keys (`realtime.ThinKeys`: `entity`, `id`, `tenantId`, `at`, `version`, `created`, `source`, `changed` and the extras of Appendix B §B.4.3, scalars only) on every topic, whatever the producer put in the outbox row (the row keeps its whole payload for RabbitMQ); a `driver:{id}` copy names no other driver. `dispatch:{partyId}:*` carries only the operational types on their own family (`realtime.DispatchFamily`: never `trip.priced|repriced`, `standby.priced`, `trip.delivered_at_changed`, `standby.customer_assigned`), `changed[]` cut to the entity's `scope_*` columns (`realtime.DispatchColumns`), and an update that changed nothing a dispatcher reads and no party (`*PartyId`) is not sent there. The party a row has just left (`leftPartyIds`, `realtime.LeftPartiesKey`) gets that event on its dispatch topic with the envelope only (`entity`, `id`, `tenantId`, `at`, `version`, `changed: []`), whatever `changed[]` names; an unreadable list gives every dispatch topic that copy. The mirror's events add `at` (the document's update time) and reach the dispatch topics of the parties after the version and, for an update of the same row, before it.
- **Frames**: `retry: 3000`; events `id: <seq>` / `event: <name>` / `data: {"type","topic","eventId","data"}`; an id-only frame with the sequence at connect; `: ping` every `SSE_PING_INTERVAL`; `reconnect` (`token_expiring` 30 s before `exp`, `shutdown`, `lagging`, `interrupted`, `roles_changed`, `connection_limit`) and `resync` (`unknown_id`, `trimmed`, `expired`, `too_far_behind`). Event names per topic: `realtime.EventName`.
- **Replay**: `Last-Event-ID: n` reads `rtlog:seq` and every log (`XINFO`, `XRANGE (n-0 + COUNT 501`) in one `MULTI`, merges by id, then streams live events above that sequence. Resync instead when `n` was never issued, a log was trimmed past it (`entries-added` above the length and the first entry after `n`), a log that expired could have held later events and `rtlog:marks` dates `n` before `RTLOG_TTL`, or more than 500 events follow on one topic.
- **Limit**: `rl:sse_conns:{userId}` is a sorted set of leases (3 x `SSE_PING_INTERVAL`, renewed by each heartbeat): the 6th stream of a user is `429 resource_exhausted` (`Retry-After: 60`), a crashed replica's leases expire. A stream whose client closes the connection ends and frees its lease at once (`watchClient` reads the connection, since fasthttp gives no disconnect signal), so a tab that recreates its stream for a new `?topics=` never holds two. Redis or the hub unavailable: `503` (`Retry-After: 3`).
- **Auth**: a live `session.revoked` for the stream's session (or `claims_changed`) ends it, and so does a live `roles.changed` on its tenant (`reconnect` `roles_changed`); ticket streams end one `JWT_ACCESS_TTL` after redemption. The connect window is covered too: `rtlog:seq` is read before the credential is checked (a handler ahead of `RequireAuth`; before the ticket is redeemed), and once subscribed the stream re-checks its session (`auth.Service.CheckSession`: `401 session_revoked` / `401 token_expired` `claims_changed`) and reads its control topics (`user:{uid}`, `tenant:{tid}:config`) from that sequence in the snapshot, so an ending event published while it connected is sent and ends it at once. Explicit `chat:{id}` topics are read under `db.WithPrincipal` (`internal/sse/queries`): the chat's driver or staff with `chat:view` in reach; a `?topics=` value outside the catalogue (or more than 20) is `422 invalid_argument` (`details.fields[0].field = "topics"`).

Tests: `go test ./internal/platform/realtime/ ./internal/sse/` (event names, hub dispatch, topic sets, query rules, opening frames; T33: the projection of every topic kind, the dispatch rules, the envelope of a party the row left, adversarial payloads with prices, parties and PII) and `make test-integration` (T33: `internal/platform/realtime` one sequence with a copy per topic in the logs and on the channels, a priced event on a dispatch topic only taking no number; `internal/sse/ops_integration_test.go` a 3.x write in the in-process Firestore applied by the listener at the default 2 s interval and relayed to a tenant's staff and a dispatcher of the work's party within 5 s (measured about 2 s) with no billing, party or cost key on the dispatch copies, a trip that leaves the dispatcher's party as it is delivered reaching it as the envelope only, and the dispatch column lists against the `scope_*` views; `internal/etl/mirror_topics_integration_test.go` `at`, the parties before and after a party change with `leftPartyIds` and the projected copies, a claim of another driver's trip and a Q3 copy reaching only their own parties; `internal/sse`: two replicas on one PostgreSQL 18 and Redis 7, a revocation made on replica A reaching a stream on replica B through the relay, replay across topics, every resync reason, the 6th stream, tickets on both listeners, chat visibility, token expiry, shutdown, an interrupted subscription, a revocation / claims change / `roles.changed` published inside the connect window before the subscription and before the snapshot, and the bounded final write).

## Redis layer (T09, main spec §2.1, Appendix B §B.6)

Every key and channel is `lt:{APP_ENV}:{namespace}:...` with the eight namespaces `cache`, `auth`, `rbac`, `idem`, `rl`, `rt`, `rtlog`, `lock` (R26); keys come only from `cache.Keyspace` builders (one per row of Appendix B §B.6.2 and Appendix C §C.4.14). The server runs AOF with `maxmemory-policy noeviction` (compose and `cachetest`, which reads the image and flags from `deploy/docker-compose.yml`).

| Env | Default | Used by |
|---|---|---|
| `REDIS_URL`, `REDIS_KEY_PREFIX`, `REDIS_TLS` | prefix `lt:{APP_ENV}:` (anything else is refused), TLS off | `cache.Open` (lazy dial; context deadlines honoured; dial 2 s, read and write 1 s, pool wait 1 s, one retry, unless the URL's query sets them) |
| `CACHE_TTL_HUBS`, `CACHE_TTL_RATECARD`, `CACHE_TTL_SETTINGS` | `10m`, `1h`, `5m` | `cache.TTLs` |
| `IDEMPOTENCY_TTL` | `168h` | `idempotency.Config` |
| `RATE_LIMIT_ENABLED`, `RATE_LIMIT_LOGIN`, `RATE_LIMIT_PUBLIC_FORMS`, `RATE_LIMIT_EVIDENCE` | `true`, `10/1m`, `5/1h`, `60/1m` | `ratelimit.Config`: `login_ip`, `public_form_ip`, `evidence_ip`; other buckets are code constants |

`.env.example` ships exactly these defaults (`TestEnvExampleShipsTheDesignDefaults`). A local `.env` made from an earlier `.env.example` keeps the old values `CACHE_TTL_RATECARD=10m`, `CACHE_TTL_SETTINGS=1m`, `RATE_LIMIT_LOGIN=10/15m`, `RATE_LIMIT_PUBLIC_FORMS=5/1m` until you edit them or rerun `make env FORCE=1`.

Every Redis call is bounded: 300 ms in the caches, the rate limiter and the idempotency middleware, 1 s for an invalidation. A Redis that accepts connections but never answers therefore costs a request at most one such bound before the fallback (loader, fail open, PostgreSQL alone) answers (`TestHungRedis*`, against a listener that never replies).

- **Caches are UI hints.** `cache.GetJSON`, `HubMaps` (two hashes `cache:hubs:n2c` and `cache:hubs:c2n`, written and dropped together, never merged), `PeriodLocks`, `Subtenants` read through to a loader (PostgreSQL) and fall back to it when Redis fails. Writers call `Cache.Invalidate` / `Cache.OnEvent` after commit; the outbox relay (T10) calls `OnEvent` for every event; deletions go out on `rt:cache` so replicas running `Cache.Run` drop their `WithL1` copies. An event that does not name the id (for example `statement.*` without `billingPartyId`) drops every key of its family. Each invalidation first increments `cache:gen:{family}`, and a read-through stores what it loaded only while that counter is unchanged, so a reader that loaded before a commit never writes the old value back.
- **Money paths never read Redis** (R17). Pricing, period locks, invoice numbering and payroll run under `cache.MoneyPath(ctx)`: every command of a guarded client fails with `ErrMoneyPath` before it is sent, and the caches refuse to serve. `go list -deps` of the pure engines must not contain `go-redis` (`TestMoneyEnginesNeverLinkRedis`).
- **Idempotency** (`httpx/idempotency`): mount `Middleware.Handler()` after authentication on each `✱` route; 2xx answers replay byte for byte (`Idempotent-Replayed: true`) from Redis (24 h) or `idempotency_keys` (until `IDEMPOTENCY_TTL`), a different body is `409 idempotency_conflict`; `PGStore.Prune` is the `idempotency.prune` job. The route runs under a 25 s deadline (`HandlerBudget`, inside the 30 s lease): **a `✱` handler must do its database and storage work under `c.Context()`**, so a request that cannot finish is cancelled and rolled back before a retry could take its claim over.
- **Rate limits** (`httpx/ratelimit`): `Limiter.Middleware(enabled, rules...)`; a request is counted when it is checked (no peek, so parallel requests cannot all pass); subjects are stored as a sha256 prefix (pseudonymous, not anonymous); `ByIP` limits an IPv6 client by its /64; fail open (logged and counted) when Redis does not answer within 300 ms. A rule without a usable limit panics when the route is built, and `Config.Validate` refuses an unusable `RATE_LIMIT_*` value, so nothing fails open by mistake. The api builds one `Limiter`: `internal/auth` checks its buckets (`login_ip`, `refresh_session`, `sse_ticket`, `forgot_*`, `reset_ip`) through `Limiter.Allow` with the same 429 and fail-open behaviour, so every caller of a bucket spends one budget. `login_fail` is not a GCRA bucket: the sign-in lockout of Appendix C §C.4.12 lives in `internal/auth` (T05).
- **Mirror ack** (`SetMirrorAck`, `WaitMirrorAck`) for read-your-writes in P2-P7a; single-use tickets (`PutTicket`, `TakeTicket` with `GETDEL`) for `auth:pwchg`, `auth:sse`, `auth:google:nonce`.
- Wiring: `app.BuildAPI` (T05) builds the process's one Redis client with `cache.Open`, so the auth store's per-request checks get the same deadlines, and calls `cache.RouteDriverLogs(log)` so go-redis log lines go through the redacting logger; routes adopt the middleware as they land (first `✱` routes: T31, T56).

Tests: `go test ./internal/platform/cache/... ./internal/platform/httpx/...` (keyspace, events, L1, money-path guard with Redis stopped) and `make test-integration` (redis:7-alpine and postgres:18-alpine: read-through, invalidation over pub/sub, Redis stopped, GCRA, idempotency replay from Redis and from PostgreSQL, and a SCAN that every key is under the prefix and a listed namespace).

## CI (T14, main spec §17.2)

Three workflows run on pushes to `mv-go` and on pull requests into `mv-go` and `mv-go-**`; a feature branch runs `go-ci` and `CI` through its pull request, not on its own pushes, while `secret-scan` also scans each push to `mv-go-**` (the repository is public). A pull request that changes `.github/workflows/ci.yml` must also change a file under CI's `pull_request` path filter (for example its `.vibe-rules.md` Change Log row), or go-ci's `web-ci` job fails it: that filter cannot list `ci.yml`, so otherwise no CI run would execute the changed workflow before the merge. `go-ci` and `secret-scan` have no `main` trigger and deploy nothing; `CI` keeps its `main` entries, and Deploy still follows CI runs whose head branch is `main` (R90). A PR whose head branch is `main` is refused by CI's `refuse-main-head` job, so bring `main` into `mv-go` through a `mv-go-sync-<date>` branch (main spec §17.5). On `mv-go` each push gets its own concurrency group in all three, so no `mv-go` run is cancelled or dropped from the queue, and every `mv-go` push runs every go-ci job and pushes its image.
